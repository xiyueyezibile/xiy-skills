# Reply Generator

基于上下文和模板生成可直接发送的回复，目标是尽量自然、顺口、少解释，并避免明显 AI 味。

## When to use

当用户出现以下意图时使用：

- “帮我回一句”
- “怎么回他/她”
- “按嘉豪的语气回”
- “阴阳一点，但别太过”
- “像我平时说话那样回”
- “给我 2-3 个回复版本”
- “根据这段聊天生成回复”

适用场景包括：

- 私聊、群聊、熟人互动
- 职场沟通、跨团队沟通、礼貌回复
- 评论区、帖子回复、轻吐槽互动

## Core rules

生成回复时遵循这个优先级：

```text
场景安全 > 上下文语气 > 指定模板 > 默认风格补全
```

解释：

- 场景安全优先，尤其是老板、客户、跨团队、首次联系等正式语境
- 有原始对话时，优先模仿用户一侧的说话方式
- 模板提供句式骨架和语气边界，不应压过真实上下文
- 缺少上下文时，再更多依赖模板默认风格

## Input extraction

先提取这些信息：

1. 用户要回复谁
2. 当前场景是什么
3. 对方说了什么
4. 用户自己前面怎么说
5. 是否指定了模板、人设、风格词、长度要求
6. 是否存在风险：
   - 信息太少
   - 场景过于正式
   - 风格要求可能冒犯

如果用户同时给了聊天记录和风格要求，优先读聊天记录，再用风格要求做微调。

## Reference loading

优先按需读取这些文件：

1. `references/INDEX.md`
   - 快速了解有哪些模板、别名和适用场景
2. `references/style-mapping.md`
   - 当用户只描述“阴阳一点”“克制一点”“短一点”这类风格词时使用
3. `references/templates/<template>.md`
   - 读取命中的模板定义
4. `references/examples.md`
   - 当需要校准“不要 AI 味”的边界时再读

不要一次性把所有模板都混在一起。最多选 1 个主模板，必要时只参考 1 个辅助模板。

## Template selection

按这个顺序选模板：

1. 用户直接点名模板或人物语气：
   - 直接命中对应模板
2. 用户只给风格词：
   - 先读 `style-mapping.md`
3. 命中多个候选时：
   - 选择最符合场景的主模板
   - 正式场景优先选择更稳的模板

不要为了追求人设感，把正式场景写得过火。

## Context imitation

如果用户提供了聊天记录，优先模仿用户一侧的这些特征：

- 句长
- 停顿方式
- 常用词
- 句尾习惯
- 情绪强度

注意：

- 模仿语感，不机械照抄
- 不要硬塞模板口头禅
- 不要把一条简短回复写成解释型段落
- 正式场景允许比原始上下文更稳一点

## Output format

默认输出：

1. 如有必要，先给一句极短的风险提示
2. 提供 `2-3` 个候选回复
3. 明确给出一个推荐项

建议格式：

```md
风险提示：
这个场景如果太冲，容易显得攻击性偏强，下面先给偏稳一点的版本。

候选 1：
...

候选 2：
...

候选 3：
...

推荐：
候选 2
```

补充要求：

- 如果用户明确说“就一句”，只给一句
- 候选之间要有明显差异，不能只是换同义词
- 默认不要解释“为什么这么写”
- 回复必须可直接复制发送

## Exception handling

### 上下文不足

如果信息太少，不要先卡死在追问上。先用一句话提醒信息不足，然后给 `2` 个偏保守候选。

### 风格和场景冲突

如果用户要求和场景明显冲突，例如：

- “很阴阳地回老板”
- “帮我怼客户”
- “第一次联系就熟人语气”

先提醒风险，再给更稳的版本，推荐项必须偏安全。

### 风格过于抽象

如果用户只说“有感觉一点”“你看着回”，优先根据已有上下文生成，不必强行追问。

## Hard boundaries

避免这些问题：

- 明显 AI 总结腔
- 客服式礼貌套话
- 鸡汤句式
- 大段排比
- 过度解释
- 在正式场景里生搬硬套熟人模板

## Examples of user requests

- “你帮我回一句，别太官方。”
- “按嘉豪那个味道回，轻一点。”
- “下面这段聊天，给我 3 个版本。”
- “帮我回老板一句，礼貌但别太软。”
