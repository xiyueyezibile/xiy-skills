# 消息面选币与交易计划

用可追溯的近期消息寻找候选币，再用 Binance 真实行情与用户授权的只读账户数据验证市场是否已经定价。每次建议前先读取本地 LLM Wiki；每次完整平仓后复盘并沉淀可复用经验。

## 权限边界

- 仅在用户明确授权时，通过安全输入脚本把 Binance API Key/Secret 保存到 `<项目根目录>/.crypto/config.json`。默认只调用 GET 只读接口；真实交易要求 Binance API 管理中只开启 U 本位合约交易权限，并继续关闭现货、提现与转账权限。
- 密钥文件权限必须是 `0600`，目录权限必须是 `0700`；不得在命令参数、对话、日志、Wiki、交易记录或错误信息中输出密钥。
- 不需要、不得请求或使用提现、转账、现货交易权限。建议使用独立 API Key、可信 IP 白名单和最小权限；用户把凭证贴入对话时提醒立即轮换。
- 没有逐单确认令牌时，不调用下单、撤单、调杠杆或修改保证金模式等写接口。选币、复盘、查仓和用户仅说“开仓”“按建议操作”都不构成交易确认。
- 真实执行支持一笔 U 本位永续市价开仓、1–3 级固定数量 reduce-only 止盈和一个关闭剩余仓位的整仓止损；近价限价、加仓、反手和移动止损继续由用户手动执行。每一级止盈价格与数量由当轮行情结构决定，禁止写死 50/50。
- 不声称保证盈利。若证据不足、数据过期或风险收益比不合格，明确输出“观望”。
- 默认只读时建议关闭现货交易、合约交易和提现；启用半自动交易后只增加合约交易，仍关闭现货、提现与转账并限制可信 IP。

## 用户确认后的半自动执行

真实资金操作采用不可跳过的两阶段流程，目的是让“研究计划”和“交易授权”保持分离。

### 生成订单草案

完成本轮账户审计、行情刷新和交易计划后，只为“当前价格仍满足门禁的市价单”生成草案：

```bash
python3 scripts/binance_confirmed_trade.py prepare \
  --plan-id PLAN_ID --symbol BTCUSDT --side LONG --quantity 0.01 \
  --leverage 5 --margin-type CROSS --stop-loss 62000 \
  --take-profit-level 66000:0.006 --take-profit-level 68000:0.003
```

`prepare` 不调用任何 Binance 写接口。它会复核交易规则、数量、最小名义金额、价格方向，并在 `<项目根目录>/.crypto/confirmations/` 写入默认 10 分钟有效的只读订单草案。向用户完整展示交易对、方向、数量、杠杆、全仓/逐仓、参考价、止损、止盈和到期时间，然后要求用户回复草案返回的精确短语：`确认执行 TOKEN`。用户明确要求确认后直接按当时市价成交，因此执行阶段不再设置价格漂移拒单门槛。

不得替用户补全确认，不得把“好”“开吧”“按这个来”等模糊回复解释为确认。草案过期、计划参数变化或用户要求重新选币时，废弃旧草案并重新生成。

### 执行已确认订单

只有用户在当前对话明确给出未过期的精确令牌后，才调用：

```bash
python3 scripts/binance_confirmed_trade.py execute --token TOKEN --confirm TOKEN
```

执行脚本会再次检查到期时间、账户持仓模式、交易规则、同币种已有仓位和残留算法保护单，并记录执行前最新标记价；随后设置杠杆/保证金模式、提交唯一 client order ID 的市价主单，通过 USD-M `algoOrder` 按草案逐级挂 `MARK_PRICE` 触发的固定数量 reduce-only 止盈，并挂一个 `closePosition=true` 的整仓止损保护所有剩余仓位。脚本检测到同币种任何已有仓位或残留算法单时必须拒绝执行。

止损保护单失败时，脚本取消所有已挂止盈并尝试立即 reduce-only 市价平仓；若紧急平仓也失败，必须用“存在未保护真实仓位”最高级别告警。部分止盈挂单失败但止损成功时保留止损和已成功止盈，明确报告部分保护，不能冒充完整成功。止损先触发后，未触发的固定数量止盈因为 reduce-only 不得反向开仓；后续审计必须识别并清理残单，清理前阻止同币再次开仓。

执行成功后立即用私有快照核对真实成交、仓位和保护单，按实际成交均价与数量调用 `crypto_memory.py open`，完整理由来自确认前保存的计划。后续每次触发继续检查仓位归零后的残留 `closePosition` 条件单；新开同币仓前必须清理或明确阻断旧保护单。

## 本地状态与学习闭环

固定使用项目根目录下的 `.crypto`。首次使用先执行：

```bash
python3 scripts/crypto_memory.py init
```

脚本会从当前工作目录向上寻找 `.git` 或 `AGENTS.md` 来定位项目根目录，并把密钥、流水和 Wiki 写入该根目录的 `.crypto`；找不到项目标记时退回当前工作目录。实际执行时推荐把命令的 `workdir` 设为要保存凭证的项目根目录；如需指定其他根目录，可设置 `CRYPTO_ROOT=/path/to/.crypto`。

目录结构、读写门禁、交易生命周期和知识沉淀格式见 [references/llm-wiki.md](references/llm-wiki.md)，涉及建议、开仓、平仓或学习资料时必须先完整读取该文件。

每次提出新建议前必须执行：

```bash
python3 scripts/crypto_memory.py context
```

读取返回的 `llms.txt`、`index.md`、`knowledge/advantages.md`、`knowledge/pitfalls.md`、`knowledge/rules.md` 以及相关交易复盘。读取失败时停止给出新建议并说明原因，不能绕过学习门禁。

### 每次触发时的交易生命周期审计

该审计不是用户提醒后才做的可选步骤。只要本 Skill 被触发，无论用户是选币、问持仓、补数量、学习资料还是要求复盘，都先执行 `context`，再执行 `binance_private_snapshot.py`。脚本会同时返回 Binance 当前真实持仓、`ledger.jsonl` 中仍打开的记录、两者的方向/数量差异，以及仅针对差异币种读取的近期成交。

按以下顺序主动处理，完成后才能继续用户当前任务：

1. `UNTRACKED_ACTIVE_POSITION`：检查近期成交和最近一次推荐。能够唯一匹配时，按实际成交方向、加权价和数量补记 `OPEN`，理由必须来自推荐当时保存的信息；无法唯一匹配理由或成交批次时，只询问无法从账户发现的最少信息。
2. `QUANTITY_CHANGED`：用近期成交识别加仓或部分平仓并追加相应生命周期事件，不得把当前持仓均价误当作每一笔原始成交价。无法区分手动调仓与成交聚合时，报告差异并询问。
3. `LOGGED_POSITION_NOT_ACTIVE`：检查近期成交判断是否已经全部平仓。能够重建实际退出数量、均价和费用时完成 `CLOSE` 并立即复盘；数据不完整时标记“疑似已平仓待确认”，不能静默关闭，也不能继续把它计入当前风险。
4. 无差异时确认 `lifecycleAudit.status=ALIGNED`，不要让用户手动提醒读取开仓记录。

Binance 当前持仓和成交是账户事实来源，`ledger.jsonl` 是研究理由与复盘来源；二者冲突必须显式处理。审计只调用 GET 只读接口，绝不因此获得下单、撤单或修改仓位权限。

用户明确说已采纳建议并开仓时，立即记录；缺少币种、方向、实际入场价、数量中任何一项时只追问缺项。记录前把原推荐理由写入临时 JSON，确保交易流水本身包含跨对话复盘所需的证据快照，不能只保存 `plan-id` 或依赖聊天历史：

```bash
python3 scripts/crypto_memory.py open --symbol BTCUSDT --side LONG --entry 64000 --quantity 0.01 --plan-id PLAN_ID --rationale-file /tmp/crypto-plan-rationale.json
```

理由 JSON 必须包含非空字段：`strategyMode`、`batchId`、`portfolioContext`、`summary`、`catalyst`、`technicalSetup`、`derivativesConfirmation`、`tradePlan`、`positionSizingReason`、`invalidation`、`confidence`、`dataCutoff` 和非空 `sources` 数组。单币计划也要写 `strategyMode=single`，并说明它不属于篮子批次。内容应记录当时可知的信息，包括消息催化与发布时间、4h/1h/15m 结构、成交量/OI/资金费率、方向与入场方式、止损止盈依据、净盈亏比、仓位风险档和杠杆依据、组合风险、失效条件、数据截止时间及来源链接。某项数据不可得时明确写“不可得”及其对置信度的影响，不能虚构。脚本会把完整对象嵌入 `OPEN.rationale`；临时文件不得包含密钥或账户标识。

用户明确说已全部平仓时，记录实际出场价、时间、费用和备注：

```bash
python3 scripts/crypto_memory.py close --trade-id TRADE_ID --exit 66000 --fees 0
```

随后必须基于原建议、开仓记录、持仓期间消息与量价、实际出场结果完成归因分析，并写入 `reviews/<trade-id>.md`。只把跨交易可复用且有证据的优势、坑位或条件式规则更新到 Wiki；不得因为单笔盈亏就武断改规则。

加仓或部分平仓时使用 `adjust` 追加事件，正数表示加仓，负数表示部分退出；全部退出仍使用 `close`：

```bash
python3 scripts/crypto_memory.py adjust --trade-id TRADE_ID --quantity-delta -0.005 --price 65000 --fees 0.2
```

用户主动提供学习资料时，记录来源、时间、摘要、适用条件、反例和可信度到 `sources/`，再把验证后的稳定结论写入 `knowledge/` 并更新索引。密钥、个人隐私和大段受版权保护的原文不得进入 Wiki。

## 账户数据与交易门禁

配置密钥时使用隐藏输入，避免 shell 历史泄露：

```bash
python3 scripts/crypto_memory.py configure-binance
```

每次触发本 Skill 都必须执行，而不只是给出可执行交易建议前：

```bash
python3 scripts/binance_private_snapshot.py
```

私有数据用于生命周期审计，以及判断账户权益、可用余额、现有仓位集中度和风险暴露，不在非必要时完整展示。若读取失败或没有配置，明确说明本轮无法完成自动对账；允许继续处理纯学习资料或输出非可执行观察名单，但不得给出具体开仓数量、名义仓位或杠杆，也不得称为可执行建议。拥有密钥、密钥具有合约交易权限和用户逐单确认是三个不同条件，缺一不可。

## 默认范围

- 市场：Binance U 本位永续合约，允许做多和做空。
- 用户明确要求股票代币、bStocks 或 TradFi perpetual 时，进入股票代币专用分析：区分底层上市公司消息与 Binance 合约/交易工具消息，行情脚本必须显式使用 `--include-tradfi` 或 `--tradfi-only`，并标注 `TRADIFI_PERPETUAL`、`underlyingType`、底层股票交易所、合约 24/7 与股票交易时段错位。不把 Binance 上线、tick size 或资金费率调整直接写成底层公司利好。
- 短周期轨道使用 4h 定方向、1h 确认、15m 入场；中长线轨道使用 1d 定市场状态和主趋势、4h 构建交易结构、1h 择时，15m 仅用于减少成交偏差，不能用 15m 噪声推翻日线逻辑。
- 支持三种策略模式：`single` 单币精选、`basket` 滚动篮子、`medium_long` 中长线波段。用户要求多币种、十几个仓或埋伏高盈利币时默认使用 `basket`；用户提到中长线、波段、持有几天/几周时启用 `medium_long`，并与篮子并行输出而非替代篮子。
- 单币精选模式：净盈亏比 `>1 且 <1.5` 时风险通常不超过权益 `0.5%`；净盈亏比 `1.5–3` 通常为 `0.75%`；证据全部共振且保守净盈亏比 `≥3` 的 A+ 机会才可使用 `1.25%`。
- 篮子探索模式分为真实开仓层、观察层和纸面追踪层：每轮评估 `8–20` 个标的，但真实开仓只取合格子集；严格门禁下允许实际持仓仅 `3–6` 腿，候选充分且风险分散时再扩展到 `8–12` 腿、上限 `15` 腿。2–4 个核心仓每个风险 `0.4%–0.6%`，其余侦察仓每个风险 `0.15%–0.3%`，任何一腿不得超过 `0.6%`。不得为了凑开仓数量纳入低流动性、同风险簇拥挤、缺少结构止损或净盈亏比不合格的币。
- 中长线模式默认持有 `3–21` 天，以高流动性主流币和具备可验证持续催化的标的为主；每轮展示 `3–8` 个候选、最多给 `1–3` 个新计划。单腿风险通常为权益 `0.2%–0.5%`，中长线桶连同已有同方向敞口的计划止损总风险不得超过权益 `1.25%`。在当前策略样本尚未单独验证前不得提高该上限。
- 中长线默认使用 `2x–4x`、硬上限 `5x`，优先逐仓；止损放在 1d/4h 结构失效位之外并至少覆盖正常日线波动，以更小数量容纳更宽止损。预计持有期内的累计资金费率、重大解锁和宏观事件必须计入净盈亏比。
- 逐仓与全仓均可建议，默认优先逐仓；只有私有账户快照可用、全部合约持仓和组合风险可核算、无对冲关系不明的仓位、强平压力测试通过时，才可建议全仓。全仓只表示共享保证金，绝不表示把全部余额作为仓位或允许扩大止损风险。
- 建议有效杠杆通常为 `3x–7x`、硬上限 `10x`。高波动、低流动性、消息不确定或强平缓冲不足的标的必须降低杠杆或淘汰。
- 用户的进攻目标是月度账户收益 `100%+`，这是策略设计与复盘基准，不是承诺、预测或强制交易配额。不得为了追赶月目标放宽消息质量、结构止损、流动性或风险闸门。
- TP1 保证金收益率约 `50%` 是优先偏好，不是固定收益要求。先由行情结构、波动率和消息持续性确定止损、分批目标与尾仓退出，再计算实际保证金收益率；禁止为了凑 50% 虚构目标或迁就止损。
- 最低门槛使用扣除预估手续费、资金费率和滑点后的保守净盈亏比，必须严格 `>1`。优先选择 `≥1.5`，`≥3` 才有资格进入最高风险档；盈亏比不等于胜率，仍须通过消息、结构和拥挤度门禁。
- 排除：稳定币相关标的、杠杆代币、非 `TRADING` 永续合约、低流动性标的及已知临近下架标的。
- 单币精选模式默认最多展示 5 个候选、推荐 3 个计划；篮子探索模式默认展示 `8–20` 个候选，但必须标注为 `可开仓`、`差一项触发`、`只观察` 或 `淘汰`，只对 `可开仓` 标的给真实交易计划和确认草案。

用户明确指定现货、周期、币种、方向或风险偏好时，以用户要求为准，但权限边界不变。当前脚本只覆盖 U 本位永续；现货任务直接调用 Binance 现货公共接口或说明脚本范围，不要把合约数据冒充现货数据。

股票代币不属于普通加密项目。若用户只想分析股票代币消息面并输出报告，优先使用 `crypto-news-analysis-report` 纯分析流程，不读取账户、不计算仓位、不生成订单。

## 工作流

### 1. 明确时间锚点

记录当前绝对时间、时区和研究截止时间。新闻发布时间、行情抓取时间都使用绝对时间，避免使用“刚刚”“今天”却不注明日期。

### 2. 建立信息差候选池

先找信息差，再做市场验证。默认不能先用涨幅榜、跌幅榜、成交额榜或技术形态决定核心候选；这些榜单前列通常代表利好/利空已经至少部分落地，只能作为验证雷达或补漏线索。

信息差候选池优先来自：

1. 未来 1–30 天有明确时间的解锁、网络升级/硬分叉、治理执行、上线/下架/结算、空投/质押/ETF/指数调整、财报、监管听证/投票/裁决；
2. 已公告但未完全执行的订单、合作、产品发布、Tokenomics 调整、公司 IR/财报指引或监管审批；
3. 已发生但仍有二阶段窗口的事件，例如公告已出但生效未到、投票已通过但执行未开始、财报日期已公布但业绩未披露；
4. 可验证的新叙事或新项目线索，但必须回到官方公告、交易所公告、链上数据、公司 IR/财报或监管文件确认。

每轮输出必须把候选拆成两栏：

- `提前埋伏池`：未来节点明确、尚未完全兑现、价格未明显抢跑、结构止损近。
- `已启动确认池`：涨跌幅/成交额已经启动，消息强但多半已部分定价，只能等回踩承接或突破后回踩确认。

不得把 `已启动确认池` 伪装成提前埋伏；不得先看到暴涨/暴跌，再给它匹配泛泛叙事、旧闻或时间缺失的消息。

### 3. 用行情雷达验证候选

从 Skill 目录执行：

```bash
python3 scripts/binance_market_snapshot.py scan --limit 30
```

脚本只调用 Binance 公共只读接口，返回当前可交易永续合约、价格、24h 涨跌幅、成交额和成交笔数。它用于确认流动性、发现已启动/已定价标的和补漏，不是核心候选主入口。

从 `scan` 发现的币，必须回到消息面取证。若找不到可追溯消息、未来节点或未完全定价路径，只能标为 `只观察` 或 `技术侦察`，不能写成消息面核心机会。

若用户指定币种，执行：

```bash
python3 scripts/binance_market_snapshot.py analyze --symbols BTCUSDT,ETHUSDT
```

这会抓取 1d、4h、1h、15m K 线并计算 EMA20/EMA50、RSI14、ATR14、近期高低点与成交量相对值。脚本输出中的 `generated_at` 和各周期最后一根 K 线时间必须进入新鲜度判断。

### 4. 搜索消息催化剂

短周期轨道对候选池逐个联网搜索最近 72 小时消息；中长线轨道同时检查最近 30 天的持续催化与未来 30 天的已排期事件，并按以下顺序取证：

1. 项目方、基金会、交易所和监管机构的官方公告；
2. 可直接定位原始材料的主流新闻报道；
3. 经交叉验证的行业媒体；
4. 社交平台仅作线索，不能单独成为入场依据。

每条采用的消息必须记录：事件、来源名称、原始链接、明确发布时间、事件发生/生效时间、检索时间、距当前多久、时效性等级、交易有效窗口，以及它为何可能影响供需、流动性、监管预期或市场叙事。单币核心仓至少两项独立证据支持核心催化；若只有一项官方一手来源，可以保留但降低置信度。篮子侦察仓允许使用一项可追溯来源，或在没有新消息时以技术/资金流模型入选，但必须明确标为“技术侦察”，不得把它描述成消息驱动机会。

区分事件发生时间和文章发布时间。回复用户时必须显式写出每条核心消息的 `发布时间`、`事件发生/生效时间` 和 `时效性`；没有明确时间、只有截图或匿名爆料的消息，不得作为核心催化。重复转载算同一来源。

时效性统一分级：

- `实时`：发布时间或事件生效时间距当前 ≤ 6 小时；
- `新鲜`：6–24 小时；
- `仍有效`：24–72 小时，且事件影响未完成或仍有后续窗口；
- `中长线有效`：3–30 天，且有持续采用、治理、监管、解锁、升级等后续路径；
- `过期/已兑现`：超出窗口，或事件已完成且缺少后续路径；
- `时间缺失`：无法确认发布时间或事件时间，只能作为待验证线索。

### 5. 评估消息是否已被定价

将消息时间与 15m/1h K 线对齐：

- 消息后放量突破且回踩守住关键位，才考虑顺势计划；
- 消息利好但价格冲高回落、量价背离，标记“可能已定价”，不追多；
- 消息利空但价格拒绝下跌，警惕空头拥挤，不追空；
- 消息发布前已大幅异动，检查是否存在提前交易，降低置信度；
- 找不到可验证催化时，单币精选模式只能列为技术观察；篮子模式可进入小风险“技术侦察仓”，前提是流动性、结构止损、衍生品数据和净盈亏比均合格。

中长线消息必须能持续影响未来数天至数周的供需或估值，例如协议升级、代币经济变化、可核验的采用进展、监管节点或宏观流动性变化。一次性社交热度、已完成空投和缺少后续路径的旧闻只能降为观察；预期事件要同时检查解锁、资金费率和“买预期卖事实”风险。

### 6. 技术面确认

按从高到低周期判断：

- 4h：EMA20/EMA50 关系、市场结构高低点决定主要方向；
- 1h：确认突破、回踩、趋势延续或反转结构，并检查 RSI 是否过度拥挤；
- 15m：寻找实际触发位，不使用单根瞬时尖峰作为入场价；
- ATR14：校验止损是否覆盖正常波动；止损应位于结构失效位之外，而非只按固定百分比；
- 成交量：突破时应有量能确认，回踩时量能宜收缩。

中长线按独立逻辑确认：1d 判断 EMA20/EMA50、摆动高低点和日线收盘是否同向；4h 必须形成突破回踩、趋势延续基地或有证据的反转结构；1h 只负责择时。中长线止损不得取 15m 局部低点/高点，日线收盘破坏主结构、持续催化被证伪或预计持有期资金费率侵蚀目标时才判定逻辑失效。每天和重大事件后重估一次，不因盘中单根尖峰频繁反手。

技术条件用于选择“现在市价入场”或“近价限价入场”：

- 市价：所需收盘、突破或回踩已经发生；草案生成时记录参考价，用户精确确认后按执行时市价成交，不使用价格漂移拒单门槛。
- 近价限价：4h/1h 方向和消息逻辑已经成立，仅等待价格回到已验证的 15m 支撑/阻力或突破回踩位。挂单价距离最新价不得超过 `min(0.5%, 0.25 × 15m ATR / 最新价)`，且挂单成交后的保守净盈亏比仍须严格大于 1。
- 限价单默认有效期 `30 分钟`。超过有效期、15m 收盘破坏原结构、核心消息被证伪、BTC 出现反向剧烈波动或最新价偏离重新报价阈值时，要求用户取消挂单并重新分析。
- 不推荐远价抄底摸顶、无限期 GTC 挂单或只因“价格更便宜”而缺少结构依据的挂单；不得把限价单描述成必然成交。

### 7. 计算交易计划

先读取本轮私有账户快照，再用最新市价、结构止损和账户风险反推仓位。不得先选杠杆再倒推可承受亏损。

做多：

- 风险 `R = 入场参考价 - 止损价`
- 目标收益风险比 `RR = (止盈价 - 入场参考价) / R`

做空：

- 风险 `R = 止损价 - 入场参考价`
- 目标收益风险比 `RR = (入场参考价 - 止盈价) / R`

止损和止盈金额不得固定。止损必须位于结构失效位之外并通过 ATR 校验；止盈使用前高/前低、密集成交区、影线回补、流动性区或趋势扩展。至少给出一个保守可达目标用于计算净盈亏比，并可给出 TP1、TP2 和移动止损尾仓。强趋势中允许让利润奔跑，但必须写清尾仓退出条件。若价格精度无法确认，保留合理小数位并提醒下单前以 Binance 规则复核。

每个可执行建议都分配唯一 `plan-id`，并在输出里保留足以生成开仓理由快照的原始依据。用户确认成交时，先把该建议结构化为理由 JSON，再调用 `open`；禁止根据成交后的走势补写或改写推荐当时的逻辑。

收益与风险换算：

- `TP1 价格变动比例 = abs(TP1 - 入场价) / 入场价`
- `TP1 保证金收益率（未扣费）≈ TP1 价格变动比例 × 杠杆`
- 若结构 TP1 支持约 50% 保证金 ROI，可用 `偏好杠杆 = 50% / TP1 价格变动比例` 作为参考；实际杠杆仍受 `10x` 上限、账户风险和强平缓冲约束
- `保守净盈利 = 目标毛盈利 - 双边手续费 - 预估资金费率 - 保守滑点`
- `保守净亏损 = 止损毛亏损 + 双边手续费 + 保守滑点`
- `保守净盈亏比 = 保守净盈利 / 保守净亏损`，必须严格大于 1
- 对移动止损尾仓不得用无限目标抬高盈亏比；风险档只按第一个保守可达目标计算，尾仓收益属于额外上行

月度目标只用于检验策略是否具备实现路径。使用最近至少 20 笔完整交易（不足 20 笔时明确“样本不足”）计算胜率、平均盈利 R、平均亏损 R、每笔期望值与最大回撤：

- `每笔期望 R = 胜率 × 平均盈利 R - 败率 × 平均亏损 R`
- 用实际交易频率和风险比例做复利情景推演，同时给出基准、乐观、压力三种结果
- 若乐观情景仍无法接近月目标，明确说明目标与当前策略统计不匹配；不得通过提高杠杆篡改胜率或期望值
- 不足 20 笔时沿用风险上限，不因样本不足提高风险；每满 20 笔重新校准一次

仓位计算：

- `账户风险额 = 账户权益 × 单笔风险比例`
- `止损距离比例 = abs(市价入场价 - 止损价) / 市价入场价`
- `风险约束名义仓位 = 账户风险额 / 止损距离比例`
- `建议杠杆 = 满足保证金占用且不超过风险上限的最小整数杠杆`
- `保证金占用 = 名义仓位 / 建议杠杆`
- `交易数量 = 名义仓位 / 市价入场价`

根据行情调整风险时，只能调整账户风险预算和数量，不能移动已经由结构确定的止损来美化盈亏比。止损距离较宽但保守目标更远、净盈亏比更高时，可以采用更高风险档；同时按止损距离缩小数量。止损距离较窄但目标空间不足时，即使杠杆收益率看起来很高也必须淘汰。

名义仓位还必须受可用余额、已有同方向/同板块仓位、维持保证金和极端滑点约束；取风险约束、组合约束和保证金约束中的最小值。计算时预留至少 `20%` 可用余额，不把全部余额用于保证金。若止损成交可能出现明显滑点，主动下调名义仓位。输出数量前按 Binance 当前数量精度和最小名义价值向下取整；无法确认交易规则时不给精确数量。

保证金模式校验：

- 逐仓：按该仓位的独立保证金和估算强平价校验。
- 全仓：按整个 U 本位合约钱包权益、所有全仓持仓未实现盈亏、维持保证金和相关性进行压力测试；至少假设其他同方向仓位同时触发止损并额外加入保守滑点。
- 只有估算强平价到入场价的距离至少为结构止损距离的 `2 倍`，且压力情景下仍未触发组合风险闸门，才可建议全仓；无法可靠估算时退回逐仓。
- 输出全仓建议时必须醒目标明：“全仓共享整个合约余额，其他仓位亏损会推近强平；建议数量不是满仓数量”。

组合风险闸门：

- 单币精选模式：所有未平仓计划按止损计算的总风险不得超过权益 `2.5%`；同方向或高度相关币种合计不得超过 `1.75%`。
- 篮子探索模式：整个批次连同已有仓位的计划止损风险不得超过权益 `4%`；同一项目生态或同一叙事桶不得超过 `1.2%`；同方向高 Beta 山寨币合计不得超过 `2.75%`。BTC/ETH 同向剧烈波动压力场景下，按所有相关腿同时止损并额外加入滑点计算。
- 中长线模式：独立策略桶上限为权益 `1.25%`，但必须与篮子和单币仓合并进行压力测试；同一币种或同一方向性逻辑不能因为贴了不同策略标签而重复计算为“分散”。已有同币同方向仓位时只给持仓管理建议，不生成第二笔自动开仓草案。
- 篮子不是把风险上限乘以币种数量。十个高度相关的山寨多单仍视为一个方向性风险簇；通过缩小每腿数量实现多样本，而不是扩大总风险。
- 全仓篮子默认使用 `3x–5x`，总名义敞口通常不超过权益 `2.0x`，预计初始保证金占用不超过合约钱包权益 `45%`；更高杠杆只用于降低单腿保证金占用，不得扩大名义仓位或计划亏损。
- 当日已实现亏损达到当日初始权益 `3%`：当天停止推荐新仓；最近 7 日回撤达到 `6%`：未来 72 小时只复盘、不推荐新仓
- 当月从权益高点回撤达到 `12%`：停止进攻档，直到完成复盘且用户明确恢复；不得用摊平、补保证金或提高杠杆追回损失
- 连续 3 笔止损：立即完成逐单与相关性复盘，重新核算当日、滚动 7 日、月度回撤和未平仓组合风险；连续止损本身不设置固定时间锁。只有实际命中上述回撤阈值时才暂停新仓。连续盈利不得自动提高单笔风险

篮子批次管理：

- 同一轮推荐共用唯一 `batch-id`，逐币仍保留唯一 `plan-id`；开仓理由记录该币在批次中的层级、叙事桶、方向、风险贡献和与已有仓位的相关性判断。
- 默认分两批建立：先开约一半候选，至少等待一个 15m 收盘后再决定其余，避免同一瞬间把全部组合暴露给一次市场噪声；若用户明确要求一次性开齐，也必须按完整组合压力场景计算。
- 候选不足时不降级门槛。真实开仓层可以少于 8 腿；观察层仍补足本轮 `8–20` 个候选，并写清每个候选缺少的关键条件，例如消息未验证、15m 二次确认不足、OI 不同向、资金费率拥挤、盈亏比不足或相关性过高。
- 对 `差一项触发` 的候选建立纸面追踪：记录触发价、失效价、原本 TP、缺失条件和后续 `4h/24h` 表现。后续复盘统计“未开仓但到达 TP”和“未开仓后失败”的比例，用于判断门槛过严或有效；纸面追踪不得计入真实盈亏、不得补写成已推荐开仓。
- 批次层面同时统计命中率、平均 R、中位数 R、最大单币盈利、最大单币亏损、前 20% 盈利贡献、相关止损数量和费用占毛利润比例。只有少数大赢家贡献收益时，不应仅以低胜率否定策略；但必须验证尾部盈利能覆盖多数小止损和交易成本。
- 同一批次多数仓位平仓后，除逐币复盘外再写一份批次复盘，比较“核心仓/侦察仓”“消息驱动/技术侦察”和不同叙事桶的效果。

杠杆建议必须同时解释：推荐倍数、预计保证金占用、止损触发时预计亏损额与占账户权益比例。明确说明杠杆不会改变按止损计划计算的亏损，但会影响强平距离和保证金占用。若预计强平价可能先于结构止损、账户已有高风险敞口，或最低可用杠杆仍不安全，则淘汰计划。

### 7. 设置否决条件

以下任一情况默认观望：

- Binance 行情抓取失败，或行情时间戳明显过期；
- 核心消息无法追溯，或只有未经证实的社交传闻；
- 公告存在下架、暂停充提、合约调整等未厘清风险；
- 24h 成交额过低、点差或插针风险显著；
- 多周期方向冲突且没有清晰触发位；
- 结构止损或目标缺乏依据、扣费后的保守净盈亏比不大于 1，或当前价已经远离计划入场区；
- BTC 出现与山寨币计划相反的剧烈系统性波动。
- 账户快照不可用、账户权益或可用余额不足，因而无法可靠计算仓位和杠杆；
- 当前价格已经越过允许滑点范围，市价成交后保守净盈亏比不再大于 1；
- 限价距离超过近价阈值、没有已验证结构位、默认有效期内成交概率和风险收益不匹配，或挂单后无法持续检查失效条件；
- 为达到约 50% 的 TP1 保证金收益率需要超过 10x 时，不强求该偏好；若降低杠杆后保守净盈亏比仍大于 1 可保留，否则淘汰；
- 命中单日、滚动 7 日、月度回撤或连续止损闸门；

## 利好/利空落地口径

报告和交易计划里的 `落地` 指**消息对应的利好或利空效应是否已经兑现**，不是事件本身是否发生。事件是否已发生只写在 `事件/生效时间`、`未来催化节点`、`当前阶段` 中。

判断标准：

- 利好落地：官方执行结果、财报/订单/监管/产品数据、供需变化、价格突破回踩承接、成交量/OI/资金费率等证据已经支持利多方向。
- 利空落地：解锁/下架/监管/故障/财报差等消息已经产生可见卖压、流动性收缩、价格破位反抽不过、成交量/OI 配合或基本面风险兑现。
- 未验证：只有标题、排期或事件已发生，但缺少供需、基本面或价格结构配合。
- 已兑现/已定价：利好/利空已经被市场充分交易，继续追入风险上调。
- 证伪/反向落地：事件发生后价格或基本面没有按预期方向传导，甚至出现反向证据。
- 下架/停止开仓/自动结算类事件：即使最终盈利，也必须复盘中途最大不利浮动（MAE）、短挤、盘口深度、资金费率/OI 拥挤和退出纪律；最终方向正确不能反推入场质量好。
- 网络升级/硬分叉/治理执行/产品发布类事件：如果仓位已经有浮盈，必须复核 TP1、移动止损、保本保护和 15m/1h 大阴线退出条件；不能等事件落地过程中让单根阴线把浮盈全部打回保本。

示例：解锁事件还没到，但价格已提前放量下破并反抽不过，可写“利空初步落地”；网络升级已完成但价格冲高回落且无生态数据改善，应写“利好未验证/反向落地”，不能因为事件完成就写利好已落地。

## 异常处理

- Binance 主域名不可达时，可尝试公开备用域名，但必须标明实际来源；所有端点都失败就停止给价。
- 新闻搜索不可用时，只能输出技术观察清单，并明确缺少消息验证，不能伪装成消息面选币。
- 某币 K 线不足时跳过该币，不以零值或其他币数据填充。
- 不把缓存、历史报告或参考仓库中的旧数值当作当前行情。
- 用户确认令牌过期、已经使用、同币种已有仓位、保护单语义不明确或订单状态未知时停止自动执行，不通过重试绕过。
