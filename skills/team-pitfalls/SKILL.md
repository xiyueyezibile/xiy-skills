# Team Pitfalls

这个 skill 的唯一目标：把对话过程中暴露出来、且“新加入团队的工程师不看这条 SKILL 写类似功能时大概率会写错”的问题，沉淀为可复用的踩坑条目，并持续更新在分类案例库中。

为了避免 SKILL.md 过长，本 skill 采用“按类型加载案例”的组织方式：只有当用户当前问题涉及某类主题时，才去读取对应的 references 文件。

## 案例索引（先读这个）

先读取索引，用于快速判断已有条目、做跨文件去重与定位：

- [INDEX.md](references/INDEX.md)

## 案例库文件索引（按需加载）

在开始沉淀/去重之前，先根据对话内容选一个或多个类型，然后只加载对应文件：

- **工具/鉴权/内部平台读取（MCP/文档/平台）**: [mcp-and-internal-content.md](references/mcp-and-internal-content.md)
- **Git/提交规范（commit/message/分支/发布）**: [git-and-commit.md](references/git-and-commit.md)
- **文档/可移植性（README/脚本/路径）**: [docs-and-portability.md](references/docs-and-portability.md)

如果现有类型都不匹配，新增一个 references/<type>.md（命名用英文-kebab-case），并在本索引中追加一行映射。

## 类型判定（快速规则）

从候选问题里抽关键词，按命中规则选 1~2 个类型：

- **工具/鉴权/内部平台读取（MCP/文档/平台）**: 关键词包含 `mcp`、`飞书`、`lark`、`docx`、`wiki`、`内部平台`、`鉴权`、`sso`、`抓取`、`拿不到内容`
- **Git/提交规范（commit/message/分支/发布）**: 关键词包含 `git`、`commit`、`提交`、`conventional`、`message`、`分支`、`rebase`、`cherry-pick`
- **文档/可移植性（README/脚本/路径）**: 关键词包含 `readme`、`文档`、`安装`、`路径`、`绝对路径`、`脚本`、`可移植`

## 触发时机

只要出现以下任一信号，就使用本 skill：

- 用户/你提到“为什么不行”“为啥拿不到”“应该怎么写才对”“容易写错”“坑”“踩雷”
- 发现工具/流程的误用（比如用不对的抓取方式、忘了某个必须步骤、误判环境能力）
- 出现规范/约定/流程导致的低级错误（尤其是新同学常犯）
- 同类问题在对话中出现第 2 次（即便单次看似偶然）

## 是否写入的唯一判断标准

判断标准只有一句：

> 新加入团队的工程师，不看这条 SKILL，写类似功能时大概率会写错吗？是则写入，否则跳过。

额外约束：

- 先判断是否是通用、可复用的模式，再决定是否写入
- 值得写入的：Web 开发者不会自然想到的模式、跨端/平台差异、工具链陷阱、流程陷阱、隐性约束
- 不该写入的：React 基础知识、特定组件的一次性实现细节、具体的 bug fix

## 写入流程（每次触发都执行）

1. 从最近对话里提取“候选问题”（0~3 个）
2. 选择类型并按需加载案例库文件：
   - 根据候选问题的标签/主题选择 1~2 个类型
   - 只读取对应 references 文件，用于去重与对齐条目格式
3. 对每个候选问题做两步过滤：
   - 可复用性：能抽象成模式/原则/步骤吗？
   - 新同学风险：不看条目会不会大概率写错？
4. 通过则写入；否则跳过
5. 写入前先去重：
   - 标题/关键词高度相似 → 更新既有条目（count + 1，补充示例/症状/解决方案）
   - 不相似 → 新增条目
6. 把条目写入选中的 references 文件（而不是写回 SKILL.md）
7. 同步更新 [INDEX.md](references/INDEX.md)：
   - 新增条目：补一行索引（ID、标题、标签、文件）
   - 更新条目：更新“最近出现”“出现次数”

## 条目格式（必须遵循）

每条踩坑用下面模板记录：

```
### P-XXX: <一句话标题>
- **标签**: <工具/平台/流程/前端/后端/跨端/...>
- **首次出现**: YYYY-MM-DD
- **最近出现**: YYYY-MM-DD
- **出现次数**: N
- **一句话结论**: <新同学最该记住的那句话>
- **容易写错的原因**:
  - <为什么直觉会错/为什么文档不显眼/为什么环境限制导致误判>
- **错误做法（反例）**:
  - <描述反例，不贴大段一次性代码>
- **正确做法（正例）**:
  - <描述正例步骤或模式>
- **最小示例**:
  - <尽量短的命令/片段/伪代码>
- **适用范围/不适用范围**:
  - 适用: <什么情况>
  - 不适用: <什么情况>
```

## 安全与边界

- 不记录任何密钥、token、cookie、内部敏感链接参数
- 不记录只对单一工程/单一页面成立的一次性细节
