# Team Pitfalls

这个 skill 的唯一目标：把对话过程中暴露出来、且“新加入团队的工程师不看这条 SKILL 写类似功能时大概率会写错”的问题，沉淀为可复用的踩坑条目，并持续更新在本文件中。

## 触发时机

只要出现以下任一信号，就使用本 skill：

- 用户/你提到“为什么不行”“为啥拿不到”“应该怎么写才对”“容易写错”“坑”“踩雷”
- 发现工具/流程的误用（比如用不对的抓取方式、忘了某个必须步骤、误判环境能力）
- 出现规范/约定/流程导致的低级错误（尤其是新同学常犯）
- 同类问题在对话中出现第 2 次（即便单次看似偶然）

## 是否写入的唯一判断标准

判断标准只有一句：

> 新加入团队的工程师，不看这条 SKILL，写类似功能时大概率会写错吗？是则写入，否则跳过。

额外约束：

- 先判断是否是通用、可复用的模式，再决定是否写入
- 值得写入的：Web 开发者不会自然想到的模式、跨端/平台差异、工具链陷阱、流程陷阱、隐性约束
- 不该写入的：React 基础知识、特定组件的一次性实现细节、具体的 bug fix

## 写入流程（每次触发都执行）

1. 从最近对话里提取“候选问题”（0~3 个）
2. 对每个候选问题做两步过滤：
   - 可复用性：能抽象成模式/原则/步骤吗？
   - 新同学风险：不看条目会不会大概率写错？
3. 通过则写入；否则跳过
4. 写入前先去重：
   - 标题/关键词高度相似 → 更新既有条目（count + 1，补充示例/症状/解决方案）
   - 不相似 → 新增条目

## 条目格式（必须遵循）

每条踩坑用下面模板记录：

```
### P-XXX: <一句话标题>
- **标签**: <工具/平台/流程/前端/后端/跨端/...>
- **首次出现**: YYYY-MM-DD
- **最近出现**: YYYY-MM-DD
- **出现次数**: N
- **一句话结论**: <新同学最该记住的那句话>
- **容易写错的原因**:
  - <为什么直觉会错/为什么文档不显眼/为什么环境限制导致误判>
- **错误做法（反例）**:
  - <描述反例，不贴大段一次性代码>
- **正确做法（正例）**:
  - <描述正例步骤或模式>
- **最小示例**:
  - <尽量短的命令/片段/伪代码>
- **适用范围/不适用范围**:
  - 适用: <什么情况>
  - 不适用: <什么情况>
```

## 安全与边界

- 不记录任何密钥、token、cookie、内部敏感链接参数
- 不记录只对单一工程/单一页面成立的一次性细节

## Pitfall Library

### P-001: 内部文档/平台内容优先走MCP而不是直接网页抓取
- **标签**: 工具, 文档, MCP
- **首次出现**: 2026-03-20
- **最近出现**: 2026-03-20
- **出现次数**: 1
- **一句话结论**: 访问内部文档/平台内容（如飞书/内部平台）时，优先用对应的 MCP/CLI 能力，不要指望通用网页抓取稳定可用。
- **容易写错的原因**:
  - 直觉会用“抓网页”解决一切，但内部站点常有鉴权/跳转/反爬/内容渲染等限制
  - 抓取成功与否不稳定，导致误判“文档不存在/链接错误”
- **错误做法（反例）**:
  - 直接用通用网页抓取去拉取内部 docx/wiki 内容，遇到空内容/跳转就放弃
- **正确做法（正例）**:
  - 先识别链接属于哪类内部系统，然后用对应的 MCP/技能读取或搜索
  - 如果拿不到全文，退化为：用检索能力定位同主题文档/片段，再补齐上下文
- **最小示例**:
  - “优先走：文档/知识库检索 → 获取 doc 内容 → 迭代读引用”
- **适用范围/不适用范围**:
  - 适用: 内部文档、知识库、平台 API 文档、受限网页
  - 不适用: 公网静态文档/无需鉴权页面

### P-002: Commit 信息应优先给一条“主线”而不是多条并列
- **标签**: Git, 流程, 规范
- **首次出现**: 2026-03-20
- **最近出现**: 2026-03-20
- **出现次数**: 1
- **一句话结论**: 默认只生成一条 commit message（一个主 type + 综合 subject），除非团队明确采用多行/多提交策略。
- **容易写错的原因**:
  - 直觉会“每个改动写一条”，但大多数仓库的提交约定是“一次提交一个主题”
  - 多条并列容易导致提交信息冗长且难以审阅
- **错误做法（反例）**:
  - 一个 commit 里写多条独立 message（看起来像多个 commit 的合集）
- **正确做法（正例）**:
  - 归纳主要变更，按优先级确定主 type（feat > fix > refactor > ...），subject 合并描述核心内容
  - 如果确实有多主题，优先拆成多个 commit，而不是在 message 里堆多条
- **最小示例**:
  - `feat: 添加A并完善B文档`
- **适用范围/不适用范围**:
  - 适用: 常规业务开发提交
  - 不适用: 团队明确要求“多行 body/多 bullet”的提交格式

### P-003: README 避免写入个人绝对路径作为安装命令
- **标签**: 文档, 工具, 可移植性
- **首次出现**: 2026-03-20
- **最近出现**: 2026-03-20
- **出现次数**: 1
- **一句话结论**: 文档里不要给读者复制个人机器的绝对路径命令，应该提供可移植的安装方式。
- **容易写错的原因**:
  - 本地调通后容易直接把本机路径粘到 README
  - 新同学照抄会直接失败，造成“工具不可用”的误解
- **错误做法（反例）**:
  - `npx skills add /Users/xxx/... -g -y`
- **正确做法（正例）**:
  - 提供仓库形式的安装（owner/repo@skill）或相对路径/发布地址
  - 如果必须本地路径，明确“示例路径需替换”为占位符形式
- **最小示例**:
  - `npx skills add <owner>/<repo>@<skill> -g -y`
- **适用范围/不适用范围**:
  - 适用: 面向团队的 README/公共文档
  - 不适用: 个人笔记且不会被团队复用
