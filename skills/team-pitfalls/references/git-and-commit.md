## Git/提交规范（commit/message/分支/发布）

### P-002: Commit 信息应优先给一条“主线”而不是多条并列
- **标签**: Git, 流程, 规范
- **首次出现**: 2026-03-20
- **最近出现**: 2026-03-20
- **出现次数**: 1
- **一句话结论**: 默认只生成一条 commit message（一个主 type + 综合 subject），除非团队明确采用多行/多提交策略。
- **容易写错的原因**:
  - 直觉会“每个改动写一条”，但大多数仓库的提交约定是“一次提交一个主题”
  - 多条并列容易导致提交信息冗长且难以审阅
- **错误做法（反例）**:
  - 一个 commit 里写多条独立 message（看起来像多个 commit 的合集）
- **正确做法（正例）**:
  - 归纳主要变更，按优先级确定主 type（feat > fix > refactor > ...），subject 合并描述核心内容
  - 如果确实有多主题，优先拆成多个 commit，而不是在 message 里堆多条
- **最小示例**:
  - `feat: 添加A并完善B文档`
- **适用范围/不适用范围**:
  - 适用: 常规业务开发提交
  - 不适用: 团队明确要求“多行 body/多 bullet”的提交格式
