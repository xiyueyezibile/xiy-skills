# Mock 数据质量规则

组件视觉验证同时验证外壳与内容。数据虽然是 Mock，也应接近该组件真实使用场景；否则空白、破图、极短文本或矛盾状态会让截图失去判断价值。

## 数据来源优先级

按以下顺序取材，并在报告中记录实际来源：

1. 目标页面和组件的真实调用点、接口类型、枚举与格式化逻辑
2. 仓库已有 fixture、story、测试数据、Mock 服务和同类页面
3. 产品文案、设计稿或用户明确给出的内容
4. 根据字段语义构造的脱敏代表性数据

不得复制 token、账号、手机号、地址等真实敏感信息，也不要触发真实写操作。无法确认关键业务语义时应标记限制，而不是随意发明会误导观感的内容。

## 填充要求

- 文本：使用符合业务语言的标题、副标题、说明和按钮文案；长度要能代表常见场景，并至少检查一个可能发生截断的合理长度
- 数值：金额、折扣、库存、计数、单位和精度符合格式化逻辑；原价不应低于售价，库存状态应与数量及按钮能力一致
- 图片：使用稳定、可访问、比例匹配且像素足够的本地资产或仓库 fixture；截图前确认没有 broken image、拉伸或低清晰度
- 枚举与状态：状态标签、颜色、辅助文案、禁用态和可执行操作保持一致，不能同时出现“已失效”和“立即使用”之类矛盾
- 列表：除非验证空态，填充足以体现间距和层级的代表性数量；各项内容略有差异，避免完全复制导致视觉密度失真
- 时间与地区：日期、时区、币种、语言和单位符合页面上下文，时间范围前后有序
- 交互：点击、选择或输入后同步更新相关字段，让前后截图体现可信状态变化

## 截图前检查

逐项观察组件，不以“React 没报错”代替视觉检查：

- 主要可见字段没有非预期空值、`undefined`、`null`、`NaN` 或 `[object Object]`
- 没有 `test`、`foo`、`xxx`、Lorem、连续重复数字等无意义占位内容
- 图片加载成功，文本没有因异常数据长度产生无意义的大块空白、溢出或布局塌陷
- 金额、状态、标签、按钮和列表之间不存在业务矛盾
- 当前数据确实对应本 case；空态、错误态和 loading case 不混入正常态内容

任一问题会实质影响截图观感时，先修正 Mock 数据再截图。若组件本身对合理数据仍出现问题，应保留证据并报告为组件表现，不能通过改成不真实的短内容来掩盖。
