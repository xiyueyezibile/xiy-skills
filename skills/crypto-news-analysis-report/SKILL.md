# Crypto News Analysis Report

这是“只分析，不交易”的消息面选币报告流程。它覆盖两类公开市场：

- 加密货币 U 本位永续：BTC、ETH、SOL、XRP 等。
- 股票代币 / TradFi perpetual：Binance 上 `contractType=TRADIFI_PERPETUAL` 的 tokenized stock futures / bStocks 相关标的，例如 `UNITREEUSDT`、`KUAISHOUUSDT`、`CXMTUSDT` 等。

它只组合：

- `crypto-news-intel`：公开消息面取证、时间和时效性判断。
- `crypto-market-structure`：Binance U 本位永续公共行情结构确认。

明确不使用：

- `crypto-risk-ledger`：不读取账户、不读取本地交易流水、不计算个人仓位。
- `crypto-trade-executor`：不生成确认令牌、不调用任何 Binance 写接口。

## 使用边界

适合：

- “只分析消息面，不看仓位和开仓”
- “帮我看看最近有哪些消息面机会，逐个币详细分析并整理 HTML 报告”
- “结合新闻和行情结构做观察清单”
- “不要读账户，只做公开数据报告”
- “股票代币也按消息面驱动来筛，不要变成纯美股财务筛选”
- “找未落地之前的消息去埋伏 / 提前布局未来催化 / 不要找已经落地的消息”

不适合：

- 要按账户余额给数量、杠杆、逐仓/全仓。
- 要生成订单草案或执行 `确认执行 TOKEN`。
- 要记录真实开仓/平仓流水。

遇到不适合场景，提示改用 `crypto-news-selector-pack` 或 `crypto-risk-ledger` / `crypto-trade-executor`。

## 数据与目录

- 只允许调用公开数据接口和网页来源。
- 可使用随包脚本：

```bash
python3 scripts/sina_finance_news.py --query "阿里巴巴,快手,寒武纪" --category stock --category hk_stock --category us_stock --limit 20
python3 scripts/binance_market_snapshot.py scan --limit 30
python3 scripts/binance_market_snapshot.py analyze --symbols BTCUSDT,ETHUSDT,SOLUSDT
python3 scripts/binance_market_snapshot.py scan --tradfi-only --limit 30
python3 scripts/binance_market_snapshot.py analyze --include-tradfi --symbols UNITREEUSDT,KUAISHOUUSDT
```

- HTML 报告默认写到项目根目录，文件名必须带 `skill-selection-report`，便于和其他临时报告区分：

```text
.tmp/crypto-news-analysis-report/<YYYYMMDD-HHMMSS>-skill-selection-report.html
```

## 报告交付硬门禁

只要本 Skill 被触发并已经产出任何选币、候选、观察清单或逐币分析结论，**必须先生成 HTML 报告文件，再最终回复用户**。不能把聊天里的 Markdown 总结当作报告交付，也不能因为用户没有逐字说“HTML”就省略报告。

执行要求：

1. 汇总公开消息、公共行情和逐币判断后，先生成结构化 JSON payload。
2. 调用随包渲染脚本：

```bash
python3 scripts/render_report.py --input <payload.json>
```

3. 读取脚本输出的 `output` 和 `file_url`，并确认 `output` 对应文件真实存在；默认输出文件名必须形如 `.tmp/crypto-news-analysis-report/20260822-1035-skill-selection-report.html`。
4. 最终回复必须把报告链接放在最前面，格式固定为：

```markdown
[打开 HTML 报告](file:///absolute/path/report.html)

HTML 绝对路径：/absolute/path/report.html
```

5. 链接和路径之后只能补 3–5 条关键结论、账户/交易边界说明和必要下一步；不要用长篇聊天正文替代 HTML 报告正文。

只有在以下情况才允许不生成 HTML 文件：

- 用户明确说“不要文件 / 不要 HTML / 只在聊天里给简版”。
- 文件系统或渲染脚本不可用，且已经实际尝试生成失败。

如果无法生成 HTML，最终回复必须用醒目的 `报告生成失败` 标题说明失败命令、错误原因和已完成的数据范围，并在聊天中补一个完整 Markdown 版 `# 消息面选币报告`；不能只给普通结论并假装已完成报告交付。

- 生成任何新报告前，必须检查项目根目录 `.crypto/position-watch/` 是否存在 active 跟踪清单。若存在，报告必须包含“已开仓催化落地跟踪”区块：
  - 跟单仓、子账户或其他交易所仓位不能因当前 Binance 主账户 API 快照无持仓而视为已平仓；用户未明确说平仓前继续视为 active。
  - 每个 active 标的都要展示：仓位来源、上次开仓催化、事件时间、当前是否落地/延期/取消、最新相关新闻、价格是否触发关键失效位、下一次复核时间。
  - 缺少方向、入场价、数量时，明确写“待补成交细节，不能计算盈亏/R 倍数/仓位风险”，但仍要跟踪消息落地情况。
- 结构化 JSON 可包含 `position_followups` 数组，渲染脚本会在摘要后生成“已开仓催化落地跟踪”区块；生成报告时不要漏传 active watchlist。
- 生成报告后，最终答复必须同时返回：
  - 可直接点击打开的 Markdown 链接，格式为 `[打开 HTML 报告](file:///absolute/path/report.html)`。
  - HTML 文件的绝对路径，便于用户在终端或 Finder 中定位。
- 不要只返回相对路径、裸路径或“已生成报告”这类不可直接打开的说明；如果渲染脚本输出 `file_url`，优先原样使用该链接。
- 如果用户指定输出路径，优先使用用户路径，但不要写入包含密钥、账户快照或私有成交的内容。
- 汇总完公开消息和行情结构后，可把结构化结果保存成临时 JSON，再用随包脚本渲染 HTML。**不得手写新的 HTML 模板，也不得使用与 `scripts/render_report.py` 不同的结构或样式**：

```bash
python3 scripts/render_report.py --input /tmp/crypto-news-analysis-report.json
```

输入 JSON 顶层字段优先使用 `meta`、`summary`、`position_followups`、`coin_reports`、`candidates`、`stock_token_refs`、`sources`；兼容旧的 `details`，但新报告不要再把候选表当主体。脚本只渲染报告，不联网、不读取账户、不读取密钥。

## 强制时间与时效性

最终回复和 HTML 报告都必须在开头写：

- `当前研究时间`：绝对时间 + 时区。
- `消息检索截止`：最后一次成功读取新闻/公告的时间。
- `行情数据时间`：公共行情脚本 `generated_at` 和 K 线最后收盘时间。
- `时效性口径`：短线 72 小时；中长线 30 天持续催化 / 未来 30 天排期事件。

每条消息必须逐条包含：

- `发布时间`
- `事件发生/生效时间`
- `检索时间`
- `距当前多久`
- `时效性等级`
- `有效窗口/复核点`
- `来源链接`

时效性等级：

| 等级 | 口径 | 处理 |
|---|---|---|
| `实时` | 发布时间或事件生效时间距当前 ≤ 6 小时 | 可进入短线核心候选，但仍需行情确认 |
| `新鲜` | 6–24 小时 | 可进入候选，重点检查是否已被定价 |
| `仍有效` | 24–72 小时，且事件影响未完成或仍有后续窗口 | 可观察或等待结构触发 |
| `中长线有效` | 3–30 天，且有持续采用、治理、监管、解锁、升级等后续路径 | 只进中长线/主题观察 |
| `过期/已兑现` | 超出上述窗口，或事件已完成且缺少后续路径 | 淘汰或只作为背景 |
| `时间缺失` | 无法确认发布时间或事件时间 | 只能作为待验证线索 |

缺少明确时间或时效性等级的消息，不得被标记为“可做”。

## 利好/利空落地口径

报告里的 `落地程度` 指的是**消息对应的利好或利空是否已经兑现到可观察结果里**，不是简单判断“事件是否已经发生”。事件本身的排期、执行或完成状态应单独写在 `事件/生效时间`、`未来催化节点`、`当前阶段` 或 `事件进度` 中。

判断 `利好/利空落地` 时优先看：

- **供需传导**：解锁是否已经产生卖压、销毁/质押/回购是否已经改变流通或需求、上线/下架是否已经影响流动性。
- **基本面传导**：财报/指引/订单/监管/产品节点是否已经正式披露，并且关键指标是否支持原来的利好或利空判断。
- **价格结构承接**：利好后是否突破并回踩守住、利空后是否破位并反抽不过；若只是事件发生但价格拒绝配合，不能写“利好/利空已落地”。
- **衍生品与流动性**：成交量、OI、资金费率、点差和交易限制是否支持该方向，而不是只看标题。

统一使用以下表述，避免混淆：

| 表述 | 含义 |
|---|---|
| `未验证` | 有消息或排期，但尚未看到利好/利空传导到供需、基本面或价格结构。 |
| `初步落地` | 已出现部分传导，例如价格突破/破位、成交量或 OI 配合、公告开始执行，但持续性仍待确认。 |
| `基本落地` | 核心利好/利空已被官方执行结果、基本面数据或价格结构承接验证，仍需监控持续性。 |
| `已兑现/已定价` | 利好/利空已经被市场充分交易，继续追入的边际收益下降，追进去风险通常上调。 |
| `证伪/反向落地` | 事件发生后没有按预期方向传导，或出现反向价格/基本面证据。 |

示例：

- 解锁事件未来才发生，但价格已经提前放量下破并反抽不过：事件进度是 `未发生`，利空落地可写 `初步落地`。
- 网络升级已经完成，但价格冲高回落、链上/生态指标未改善：事件进度是 `已完成`，利好落地应写 `未验证` 或 `证伪/反向落地`。
- 财报日期已公布但财报未披露：事件进度是 `未发生`，利好/利空落地通常是 `仅预期/未验证`，不能写已落地。

## 分析流程

1. **建立时间锚点**
   - 记录当前时间、时区、研究周期、消息检索截止。
   - 明确用户要短线、篮子观察还是中长线观察；未说明时默认短线 72 小时 + 中长线 30 天各给一栏。
   - 用户要求“未落地之前的消息”“埋伏”“提前布局”时，切换到 `pre_landing` 模式：只把未来 1–30 天有明确节点、尚未完全兑现的事件作为核心候选；已完成且没有下一阶段的消息只能作背景。

2. **消息面取证**
   - 按 `crypto-news-intel` 规则检索官方公告、交易所公告、监管文件、主流新闻和行业媒体。
   - 只保留可追溯、可写出时间和链接的消息；社媒传闻放入“待验证线索”。
   - **消息面是主驱动**：先因为明确新闻、公告、财报、监管、产品、订单或行业事件形成候选，再用行情结构确认；不要先用涨幅榜、技术形态或 FinViz 因子筛出股票后反向找理由。
   - 中文财经消息可调用 `scripts/sina_finance_news.py`，尤其用于股票代币底层公司的财报、产品、政策、回购、增发、行业新闻；但新浪财经通常是媒体源，能找到公司公告或交易所披露时仍以原始披露为准。
   - 股票代币 / TradFi perpetual 需要额外检索底层股票公司的消息，而不是只看 Binance 上线公告：
     - 公司公告、财报、业绩预告、回购/增发、重大合同、产品发布、监管/诉讼、行业政策。
     - 股票交易所公告或上市公司 IR 页面优先，主流财经媒体次之。
     - Binance 合约公告只证明交易工具上线、杠杆/资金费率/tick size 变化，不等于底层公司利好。
     - 必须写清 `底层资产`、`股票市场/交易所`、`Binance 合约生效时间`、`底层公司事件时间` 和两者是否错位。
   - FinViz / `finviz-screener` 只能作为**美股候选池辅助**：用于确认某个消息主题下有哪些美股、流动性/市值/技术条件如何；不能把 FinViz 筛选结果本身当成消息催化，也不能让财务/技术因子取代消息面主线。
   - `pre_landing` 模式必须优先找排期事件：未来交易所上线/下架/结算、网络升级/硬分叉、治理执行、解锁、主网/产品发布、财报、监管听证/投票/裁决、指数/ETF/质押/空投等；没有未来节点的已落地新闻不得进入核心。

3. **公共行情结构确认**
   - 用 Binance 公共行情确认标的是否为 U 本位永续且 `TRADING`。
   - 普通加密永续默认只接受 `PERPETUAL`；股票代币流程必须显式使用 `--include-tradfi` 或 `--tradfi-only`，并在报告中标注 `TRADIFI_PERPETUAL` 与 `underlyingType`。
   - 对候选运行多周期分析，记录 `generated_at`、各周期最后 K 线收盘时间、价格、EMA、RSI、ATR、成交量相对变化。

4. **合并判断**
   - 每个币只给分析状态，不给仓位金额：
     - `可继续跟踪`
     - `等触发`
     - `只观察`
     - `淘汰`
   - 判断依据必须同时包含消息时效性和行情结构；任何一个缺失都不能升级为高优先级。
   - `pre_landing` 候选额外标注 `未来催化节点`、`当前阶段`、`剩余时间`、`利好/利空落地程度`、`是否已被抢跑`、`提前埋伏条件`、`兑现风险`；如果已经明显抢跑，不能用“事件未发生”降低风险。

### 风险标签必须按用户执行语义校准

报告里的 `追进去风险` 会被用户用于真实开仓决策，因此不能把它当作普通形容词随意给“中”。

- 默认口径：用户很可能把 `低` / `中低` / `中` 理解为“可以开进去”，把 `中高` / `高` / `极高` 理解为“先别开或只能极小试错”。因此只要报告没有明确允许直接入场，就不要给 `中` 或更低。
- 只有同时满足以下条件，`追进去风险` 才能标为 `低`、`中低` 或 `中`：
  1. 核心消息是一手或高可信来源，并且已经写清发布时间、事件/生效时间、检索时间、时效性和有效窗口。
  2. 利好/利空至少部分落地，不只是财报前预期、分析师观点、媒体解读、主题扩散、传闻或“可能订单”。
  3. 行情触发已经发生：突破必须至少 15m 收盘站稳，回踩必须出现承接，不能只靠盘中刺破。
  4. 价格没有明显远离触发位；若刚 24h 大涨、靠近前高、RSI 偏热或量能背离，至少标 `中高`。
  5. 股票代币还必须确认底层正股或主要交易时段有承接；Binance 24/7 合约单边抢跑不能单独降风险。
- 以下任一情况，`追进去风险` 必须标 `中高` / `高` / `极高`，并在 `操作倾向` 写 `等触发`、`只观察` 或 `淘汰`：
  - 消息只是财报前预期、分析师上调、媒体观点、主题扩散，尚未被公司财报/指引/订单/监管文件确认。
  - 报告给出的关键措辞是“等待突破”“等待回踩承接”“可继续跟踪”，但触发尚未发生。
  - 已接近或刺破前高但未站稳，或 15m/1h 出现放量下杀、冲高回落、量价背离。
  - 股票代币处于美股休市/盘前盘后错位阶段，底层正股尚未确认。
- 对每个 `中` 或更低风险标签，必须同时写一句 `为什么现在可以开而不是只观察`；写不出来就上调到 `中高` 或 `高`。
- `操作倾向` 不允许含混：若不是可直接开，必须写 `等触发：具体触发条件...` 或 `只观察`，不能只写“可继续跟踪”。

5. **生成 HTML 报告**
   - 报告应自包含：标题、数据时间、摘要卡片、逐币深度分析、风险提示、来源说明。
   - 不要把报告主体做成候选列表或表格；每个币必须单独成章，用自然语言解释消息逻辑。
   - 每个币章节都要回答：消息是什么、为什么利多/利空、利好/利空效应是否已经落地/兑现、是否已经被价格交易、接下来观察什么。
   - 每个币章节顶部必须先给 `方向判断`、`利好/利空落地`、`追进去风险`、`操作倾向` 四个醒目结论，再展开论证；不要把这些关键信息埋在长段落里。
  - 股票代币章节额外回答：这是底层股票公司的消息，还是 Binance 交易工具/合约参数消息；利多/利空是否传导到该 USDT 合约。
   - `pre_landing` 报告每个币章节额外回答：未来催化节点是什么、现在处于哪一阶段、还剩多久、是否已被资金抢跑、提前埋伏要等什么价格/结构、兑现日怎么处理。
   - 如需汇总，可放 3–5 条摘要卡片；不要用长表替代逐币分析。
   - 用 CSS 做清晰排版，适合浏览器打开和截图转发。

## 固定 HTML 报告模板
