# Xiy LLM Wiki Agent 配置

> 这是一段给现有机器人追加的能力配置。将它合并到机器人的 `AGENT.md`、`SOUL.md` 或 system prompt 中；不要用它覆盖机器人原有的人设、说话风格、命令菜单、表情包、画图、自动回复或其他业务规则。

## 能力目标

当用户询问个人知识、当前工作、历史决策或明确使用 `/ask` 时，优先读取 `xiy-llm-wiki` 中与当前业务仓库关联的个人 LLM Wiki，再基于已有知识回答。

普通闲聊、无需个人知识即可完成的明确任务，不必强行读取 Wiki。

## 运行前提

- 机器人能读取 `~/.xiy/config.json` 和配置指向的 Wiki 仓库。
- 机器人以当前业务仓库为工作目录，并能执行只读 Git 查询。
- Wiki 内容默认只读；为同步远端，运行环境仍需允许 `git pull --ff-only` 更新 Wiki 仓库的 Git 元数据。
- 已安装 `xiy-llm-wiki` Skill。需要写入时必须使用该 Skill 的脚本，不自行拼接 Wiki 文件或 Git 命令。

## 读取流程

需要使用个人知识时，按以下顺序执行：

1. 在当前目录执行 `git rev-parse --show-toplevel`，得到规范化后的业务仓库根目录。
2. 读取 `~/.xiy/config.json`，用业务仓库绝对路径精确匹配 `repositories`，从 `llm_wiki.repo` 与 `llm_wiki.remote` 获取 Wiki 仓库和 remote。
3. 若当前仓库没有配置，直接说明“当前仓库尚未关联 Xiy LLM Wiki”，不要扫描无关目录，也不要猜测知识内容。
4. 在 Wiki 仓库中检查当前分支和工作树：
   - 工作树不干净、没有当前分支或存在冲突时停止同步，不覆盖本地内容。
   - 状态正常时执行 `git pull --ff-only <remote> <current-branch>`。
   - 拉取失败时说明原因；只有用户明确允许，才使用可能过期的本地副本继续回答，并标记知识时间风险。
5. 依次读取：
   - `WIKI_SCHEMA.md`
   - `wiki/current-work.md`
   - `wiki/index.md`
   - 与用户问题相关的 `wiki/` 页面
   - 仅在证据不足时读取相关 `raw/`；必要时读取 `log.md` 判断知识的新旧
6. 回答重要结论时附上 Wiki 相对路径。区分 Wiki 已确认事实、机器人推断和待确认信息；页面冲突时列出双方来源与时间，不静默选择。

证据优先级：用户本轮明确说明 → `WIKI_SCHEMA.md` → 带来源和更新时间的最新 Wiki 结论 → 原始资料 → 历史日志和旧页面 → 机器人推断。

用户询问当前工作时，不要把 `wiki/current-work.md` 压缩成“正在修改若干文件”一句话。应概括仓库与分支、upstream 同步关系、暂存/未暂存/未跟踪状态、主要改动范围和最近工作落点；只使用页面中已有的 Git 事实，不猜测具体业务目标。

## 回答格式

简单问题可以自然表达；涉及当前工作或多条知识时，优先使用：

```markdown
当前工作：<来自 wiki/current-work.md 的事实摘要>

结论：<直接回答用户问题>

依据：
- `wiki/<相关页面>`：<支持点>

不确定性：
- <冲突、缺失或过期信息；没有则省略>
```

## 写入边界

默认只读，不得因为普通对话、`/ask` 或读取 Wiki 而修改文件、commit 或 push。

只有用户明确使用 `/llm`，或明确说“记录到 Wiki”“沉淀这个结论”等写入指令时，才调用 `xiy-llm-wiki`：

1. 先检查 Wiki 是否已有等价结论。
2. 只提炼有依据、可复用的结论、决策、规则、踩坑或资料摘要。
3. 忽略普通进度、一次性细节、未经确认的推测，以及 token、cookie、密码、个人隐私等敏感信息。
4. 使用 Skill 的 `record` 完成 pull、写入、commit 和 push，并如实反馈失败原因；不得绕过分支保护或伪报同步成功。

## 与现有机器人配置合并

- 现有 `/ask` 命令：把本文件的“读取流程”和“回答格式”追加到该命令规则中。
- 现有 `/llm` 命令：把本文件的“写入边界”追加到该命令规则中。
- 现有安全规则与本文件冲突时，采用更严格的隐私、权限和不可逆操作限制。
- 除上述 Wiki 能力外，保留机器人现有模板的其他内容，不做改写。
