# PRD To Tech Code

把 PRD、已有技术方案、聊天记录、文档、手动纠正和仓库代码证据，转成统一模板技术方案；信息足够时继续按方案落代码。

## 触发场景

当用户要求以下任务时使用：

- PRD、需求文档、产品方案、飞书文档、截图文字转技术方案或代码
- 已有技术方案、技术设计、改造方案、方案草稿或任务拆解转模板技术方案，再继续落代码
- 聊天记录、会议纪要、评论讨论、口头补充或用户纠正整合进方案
- 从产品描述、技术方案或多来源上下文推进到现有仓库改造

不用于纯 PRD 润色、纯产品评审、纯视觉设计分析，除非用户要求技术落地。

## 必读引用

- 涉及业务上下文、跨轮信息、已有技术方案、用户纠正或知识沉淀时，读取并遵循 `references/llm-wiki.md`
- 输出或更新技术方案时，读取并使用 `references/technical-plan-template.md`；该模板以“共用基线 + 按需求点逐章展开 + 跨页面联调上线”为默认评审格式，不再使用旧的横向大章节模板

固定使用 `~/.prd-to-tech-code` 作为业务 LLM Wiki 根目录。

## 核心流程

```text
信息收集 -> 当前业务配置 -> 业务 Wiki -> 仓库代码 -> 缺口澄清 -> 模板技术方案 -> 执行计划 -> 代码实现 -> 知识沉淀 -> 交付
```

执行时按顺序完成：

1. 判断输入类型：PRD / 已有技术方案 / 聊天记录 / 文档 / 用户纠正 / 仓库证据
2. 读取 `~/.prd-to-tech-code/config.json`，确认或创建 `currentBusinessSlug`
3. 读取当前业务 Wiki，重点看仓库边界、代码证据、用户纠正、需求、决策和约束
4. 识别单仓库或多仓库影响面，并阅读相关仓库代码
5. 把输入补齐为模板技术方案，必须包含资料图或改造示意、仓库证据和文件级代码落位清单
6. 用户要求继续写代码时，先确认模板方案足够具体，再按仓库现有模式最小改动实现
7. 结束前把可复用来源、资料图、仓库事实、用户纠正、决策、约束或最新模板方案写回业务 Wiki

## 业务归属

`~/.prd-to-tech-code/config.json` 记录当前业务：

- 用户明确指定业务时，更新 `currentBusinessSlug`
- 没有当前业务时，基于 PRD 标题、页面名、项目名或需求目标自动创建稳定 `business-slug`
- 已有当前业务时，除非用户明确说是新业务，否则后续输入默认写入原业务
- 输入与原业务差异过大但用户未明确新业务时，先写入原业务，并在 `pendingBusinessConfirmation` 标记疑似新业务；交付时提示用户确认是否拆分

不要因为出现新页面、新接口或新仓库就自动切换业务。

## 输入处理

信息来源包括但不限于：

- PRD、产品文档、飞书文档、截图文字
- 已有技术方案、技术设计、改造方案、方案草稿、任务拆解
- 聊天记录、会议纪要、评论讨论、口头补充、用户纠正
- 设计稿说明、接口文档、数据表说明、埋点文档
- 仓库代码、配置、类型、路由、接口封装、权限和运行约束

冲突优先级：

```text
用户本轮明确纠正 > 业务 corrections.md > 仓库事实 > 已确认 decisions.md > 最新 PRD/技术方案/文档 > 旧聊天记录/旧草稿
```

## 已有技术方案输入

用户直接给技术方案时，不能直接照原方案落代码：

1. 原方案先作为来源写入 `sources.md`
2. 读取业务 Wiki 和仓库代码，校验原方案中的文件、接口、类型、状态、埋点、权限和配置
3. 按 `references/technical-plan-template.md` 归一化为模板技术方案
4. 缺少文件级代码落位清单时，必须基于仓库代码补齐；补不齐才追问
5. 归一化后的 `technical-plan.md` 是后续代码实现依据，原始方案只是来源之一

## 技术方案要求

技术方案必须能直接指导代码落位：

- 写明信息来源、业务归属、资料图或改造示意、仓库范围和代码证据
- 需要完善或改写已有评审文档时，优先采用“参考文档与证据来源 + 需求点逐章展开”的结构：总览只放资料来源、负责人边界、页面/仓库边界、共用协议、跨需求互斥和联调上线规则；每个需求点独立成章，章内就地包含现状图/目标图、用户效果、差异表、现状代码、技术实现、文件落位、状态异常、依赖与验收
- 多需求方案必须按需求点聚合信息，不要把仓库证据、协议、状态、风险、修正内容都堆成横向大章节；读者应能在一个需求点章节内看到“为什么改、改哪里、怎么改、怎么验”
- 每次根据用户纠正、源技术方案或新增证据修正文档时，必须拆回对应需求点或对应共用章节就地合入；禁止把具体实现规则追加到文末“补充说明 / 校准补充 / 后续修正”汇总章节
- 文档开头必须列“参考文档与证据来源”，包含源技术方案、目标文档、PRD、需求拆分、接口/BAM/IDL、仓库代码证据及版本或读取时间，并写清各来源用途和冲突优先级
- 回写 PRD 图、设计稿图或截图到飞书文档时，必须保持图片原始宽高比例；不得把不同尺寸图片统一写成 `512×512` 等固定正方形。插入或替换前应读取图片真实像素，按比例缩放到合适展示宽/高，并在回读后校验展示尺寸没有明显拉伸
- 区分需要修改的仓库和只读参考仓库
- 逐文件列出仓库、文件路径、现有锚点、改动类型、要写的代码、依赖复用、输入输出、异常状态和验证点
- 覆盖用户可见行为、状态分支、接口契约、权限、降级、风险和执行计划
- 如果没有现成图示，至少用 Mermaid 或 ASCII 表达用户路径、数据流、架构边界或改造前后变化

只要无法定位到文件级落点，就继续读仓库或提出最少阻塞问题；不要用抽象模块名代替。

## 评审文档组织范式

当用户要求“完善飞书 Wiki / 技术方案 / 评审文档”，且目标包含多个页面、模块、负责人项或需求编号时，默认采用以下可复用格式：

1. 标题与负责人范围
   - 标题直接说明业务、页面或负责人范围
   - 用引用块或短段落说明本方案覆盖哪些需求点、不覆盖哪些触点
2. 范围与共用基线
   - 参考文档与证据来源：表格列出“引用资料 / 链接或位置 / 版本或时间 / 在本方案中的用途”
   - 需求审计结论：对照需求拆分和直接 PRD，说明是否有遗漏
   - 页面与代码边界：页面、仓库与入口、对应需求点
   - 涉及代码仓库与页面清单：只列用户/负责人范围内要改的页面、模块和为这些页面服务的协议生成配置；列出仓库、本地路径或入口、页面/模块、本次角色、关联需求、主要文件/关注点；不要把非负责人范围的页面作为“涉及页面”列入，即使它们是只读参考或上游触点
   - 共用协议：公共接口、核心字段、影响的需求点
   - 共用展示规则：跨需求互斥、共存、降级和优先级
3. 按需求点逐章展开
   - 每个需求点使用稳定标题，例如 `PQL-03｜频道页：单单返头部与阶段 4 解锁打榜赛`
   - 先写“页面现状与改造后效果”：现状文字 + 现状图，目标文字 + 改造后图；如果没有真实图片，明确说明没有图片并用 Mermaid/ASCII 补示意
   - 紧跟视觉说明写“设计稿与视觉资源位”：即使当前没有设计稿，也要留出设计稿链接、关键切图/标注、视觉验收位置；明确标注 PRD 截图、数据来源证据、临时示意图不能替代最终设计稿
   - 图片展示必须保持原始比例：宽图按宽度缩放，长图按高度缩放；超宽表格截图可以较矮展示但不能强行拉高；长屏截图可以较窄展示但不能强行拉宽
   - 写“改造前后差异”表：区域、文案、交互、状态、数据来源、降级变化
   - 写“改造目标与用户效果”
   - 写“现状代码”：具体到仓库、文件路径、现有能力、本次处理
   - 写“协议 / 数据 / 状态”：只放本需求相关字段和状态，不把全部协议集中堆到总览
   - 写“技术实现”：按执行顺序描述复用、分支、状态和异常
   - 写“文件落位”：具体文件、改动、输入输出、异常降级、验证点
   - 写“依赖与验收”：阻塞字段、联调口径、埋点、人工验证
4. 商品/页面/跨端分组
   - 可先按大页面分组，如“频道页需求”“商品决策页需求”，组内再放需求点
   - 只读参考触点不进入负责人实施章节，只在边界或来源中说明
5. 联调上线
   - 只放跨需求关系、统一待确认项、实施顺序、上线与回滚、最终验收
   - 不承载某个具体需求点的新增实现细节

修正文档时的硬规则：

- 新增来源或证据只放在“参考文档与证据来源”
- 新增某个需求的规则、状态、协议或风险，放回对应需求点章节
- 只影响所有需求的互斥、协议基线、上线顺序，才放到共用基线或联调上线章节
- 删除或改写旧结论后必须回读 outline/关键词确认没有文末残留块或孤立标题
- 如用户明确说“这个格式满意”，将该格式写回 skill 与 README，作为后续默认模板

## 代码实现规则

- 必须基于仓库代码证据实现，不能只相信 PRD 或原始技术方案
- 必须按归一化后的技术方案和文件级代码落位清单实现；如果实现中发现方案落位不准确，先回到仓库代码证据校正方案/执行计划，再改代码
- 优先复用仓库已有目录结构、请求封装、类型系统、组件模式、工具函数和错误处理
- 保持最小改动，只修改完成需求必须涉及的文件
- 不做无关重构、无关格式化、无关文件移动、无关依赖升级，不为了“顺手优化”扩大 diff
- 新生成的源文件必须在文件顶部或核心导出附近写必要注释，说明文件职责、适用场景、主要输入输出或与需求点的关系；注释应解释业务意图，避免重复代码本身
- 修改已有文件时，仅在新增复杂逻辑、状态机、降级策略、跨仓库协议适配或非显然业务规则处补充简洁注释；不要给显而易见的代码堆注释
- 新增组件、hook、service、类型或工具时，文件名、导出名和目录位置必须贴合仓库既有命名与分层；一次性逻辑优先就近放置，通用逻辑才抽到公共目录
- 严格按仓库现有 lint/format 风格写代码；未被要求时不主动全仓格式化
- 代码改动应可逐项映射回技术方案中的需求点和文件落位清单；交付时说明“需求点 -> 文件”对应关系
- 技术方案转代码后必须生成一份 HTML 代码改动报告，默认放在当前工作区的可追踪目录下，例如 `.tmp/prd-to-tech-code/code-change-report.html`；如果仓库禁止 `.tmp` 或用户指定目录，则放到用户允许的位置
- HTML 报告必须是左右对照布局：左侧展示代码改动（文件树、diff、关键代码片段或新增文件内容摘要），右侧在每个改动对应位置展示详细说明
- HTML 报告右侧每条说明必须包含：对应需求点 / 技术方案章节、为什么要这样改、之前逻辑是什么、这次新增或修改了什么逻辑、影响的输入输出 / 状态 / 降级、人工验证点
- 报告中的代码片段应围绕实际改动，避免整文件大段复制；涉及敏感信息、token、cookie、个人隐私时必须脱敏或不展示
- 如果本轮只生成技术方案没有落代码，则不需要生成 HTML 代码改动报告；一旦写入代码或生成源文件，就必须生成并在交付中给出报告路径
- TypeScript 避免 `any` 和 `unknown`；外部 API 无法表达时用局部封装隔离
- 不凭空新增接口、字段、埋点、权限或配置；无依据时标明假设或等待确认
- 不擅自改 `.gitignore`、`.vscode`、锁文件、构建配置或全局样式；确需修改先询问
- 用户没有要求测试时，不主动新增测试；高风险改动只建议人工验证方式

## 交付

交付时用中文简明说明：

- 当前业务 `business-slug`，以及是否存在疑似新业务待确认
- 模板技术方案的关键结论、资料图或改造示意
- 文件级代码落位清单或实际修改文件
- 核心行为变化、运行方式、人工验证路径
- 假设、风险和需要用户确认的问题
