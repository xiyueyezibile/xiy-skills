# 技术方案模板（按需求点评审版）

> 使用说明：本模板以“爆品合伙人频道页 & 商品决策页技术方案”的评审格式为基准，用于把 PRD、源技术方案、需求拆分、接口协议和仓库代码证据整理成可评审、可落代码的技术方案。默认结构是：**负责人范围 + 范围与共用基线 + 按需求点逐章展开 + 联调上线**。  
> 核心原则：具体实现规则必须写回对应需求点；不要把补充内容堆到文末。每个需求点都要能回答“为什么改、改哪里、怎么改、怎么验”。

> **负责人范围：**本方案只覆盖 <负责人负责的页面 / 需求点>。<不属于负责人范围的触点> 不进入本方案实施范围；如需提及，只能在参考来源或边界说明中作为非实施项出现。

## 写作与更新硬规则

- 只列负责人范围内的页面和模块；非负责人范围触点不要放进“涉及代码仓库与页面清单”。
- 具体实现细节必须按需求点就地写入；不要新增文末“补充说明 / 校准补充 / 后续修正”来承载具体规则。
- 每个需求点必须给设计稿留位置；没有设计稿就标“待补充”。
- PRD 图、设计稿图和截图必须保持原始比例，不能统一写成 `512×512`。
- 弹窗如果是本期新增，必须明确“新增组件”；旧组件只能写为参考，不要写“复用”。
- 文件落位必须具体到仓库、文件路径、现有锚点、改动类型、输入输出、异常降级和验证点。
- 修改飞书文档后必须回读 outline / keyword，确认新内容在正确章节、没有文末残留块、没有过期路径或错误范围。

## 技术方案转代码硬规则

- 代码实现必须按本方案的需求点和文件落位清单逐项执行；如果实现中发现落位不准确，先更新方案或执行计划，再改代码。
- 保持最小改动：只修改完成需求必须涉及的文件，不做无关重构、无关格式化、无关文件移动、无关依赖升级。
- 新生成的源文件必须在文件顶部或核心导出附近写必要注释，说明文件职责、适用场景、主要输入输出或对应需求点；注释解释业务意图，不重复代码表面含义。
- 修改已有文件时，只在复杂状态机、降级策略、跨仓库协议适配或非显然业务规则处加简洁注释；不要给显而易见的代码堆注释。
- 新增组件、hook、service、类型或工具必须贴合仓库既有命名与分层；一次性逻辑优先就近放置，通用逻辑才抽公共目录。
- 不凭空新增接口、字段、埋点、权限或配置；无依据时标明假设或等待确认。
- 交付代码时说明“需求点 -> 修改文件”映射、核心行为变化和人工验证路径。

### 代码改动 HTML 报告

> 一旦本轮写入代码或生成源文件，必须生成 HTML 报告。默认路径：`.tmp/prd-to-tech-code/code-change-report.html`，也可以按用户要求放到指定目录。

报告要求：

- 使用左右对照布局。
- 左侧放代码改动：文件树、diff、关键代码片段、新增文件摘要。
- 右侧放逐改动解释，每个改动对应一份说明。
- 右侧每条说明必须包含：
  - 对应需求点 / 技术方案章节
  - 为什么要这样改
  - 之前逻辑是什么
  - 这次新增或修改了什么逻辑
  - 影响的输入输出 / 状态 / 降级
  - 人工验证点
- 不展示敏感信息、token、cookie、个人隐私；代码片段只截取与改动相关的部分。

HTML 建议结构：

```html
<main class="report">
  <aside class="left">
    <h2>代码改动</h2>
    <section class="file">
      <h3>path/to/file.tsx</h3>

    </section>
  </aside>
```
