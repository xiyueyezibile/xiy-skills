# 消息面选币协作技能包

这是消息面选币的总控 Skill。它把“消息来源判断、行情结构确认、账户/流水/仓位风控、确认式执行”拆给多个专项 Skill 协作，避免一个回答里把新闻、技术面、风险和下单混在一起。

## 协作角色

- `crypto-news-intel`：负责公开消息面取证、市场热点与传闻增量监控、证据分层、催化剂质量和是否可能已被定价。
- `crypto-market-structure`：只负责 Binance U 本位永续公共行情、1d/4h/1h/15m 结构、ATR、成交量、可交易性。
- `crypto-news-analysis-report`：只组合 `crypto-news-intel` 与 `crypto-market-structure`，输出不含账户/仓位/下单的 HTML 纯分析报告，并在最终答复返回可直接点击打开的 `file://` 报告链接和绝对路径。
- `crypto-risk-ledger`：负责项目根目录 `.crypto` 本地上下文、Binance 私有只读快照、真实持仓与流水对账、仓位数量和组合风险。
- `crypto-trade-executor`：只在用户回复精确 `确认执行 TOKEN` 后处理市价开仓与保护单；没有精确确认时只能生成草案或手动清单。
- `crypto-news-selector`：兼容旧的全流程单 Skill；在协作包中优先作为共享脚本运行时和兜底完整流程。

如果某个专项 Skill 未安装，不要假装已经完成它的职责；改为在当前回答内按对应角色的规则做降级版，并标明缺少的自动化能力。

## 报告交付优先级

用户说“用 skill 选币”“帮我选币”“消息面选币”“看看机会”“找币”“给观察清单”时，默认交付物必须包含一份可打开的 HTML 报告；除非用户明确说“不要报告 / 不要 HTML / 只在聊天里给简版”，不能只返回聊天正文。

硬要求：

1. 完成消息取证、行情结构、账户/流水审计或纯分析流程后，先生成结构化 JSON payload。
2. 调用 `crypto-news-analysis-report/scripts/render_report.py` 生成 `.tmp/crypto-news-analysis-report/<YYYYMMDD-HHMMSS>-skill-selection-report.html`。报告模板固定对齐本仓库样例 `.tmp/crypto-news-analysis-report/20260822-1035-skill-selection-report.html`，不得手写其他 HTML 结构或使用“等价但不同”的模板。
3. 生成后检查 HTML 文件存在，并把脚本输出的 `file_url` 和绝对路径放在最终回复最前面：

```markdown
[打开 HTML 报告](file:///absolute/path/report.html)

HTML 绝对路径：/absolute/path/report.html
```

4. 最终回复里的聊天摘要只保留 3–5 条关键结论、是否读取账户、是否生成订单/执行交易、下一步动作。详细逐币分析必须在 HTML 报告里。
5. 如果报告生成失败，必须在最终回复用 `报告生成失败` 单独说明尝试过的命令、失败原因、已完成的数据范围，并给出完整 Markdown 版报告作为兜底；不能悄悄省略报告。

固定报告结构必须为：`数据时间` -> `结论摘要` -> `市场热点参考` -> `风险与落地速览` -> `逐项研究审计`（全市场模式必填）-> `已开仓催化落地跟踪`（仅有 `position_followups` 时）-> `逐币消息面深度分析` -> `股票代币 / TradFi 合约信息`（仅有股票代币引用时）-> `摘要矩阵`（仅有 `candidates` 时）-> `来源列表` -> `声明`。桌面端必须提供左侧固定目录并能跳到热点、每个持仓和逐币章节；其中 `摘要矩阵` 必须放在逐币深度分析之后，不能替代逐币章节。

## 持仓后持续跟进

用户声明“我开了/我进了/我有仓位”某些标的后，必须进入 `position_followup` 跟踪状态，而不是只回答一次。

- 先调用 `crypto-risk-ledger` 审计账户与本地 ledger；如果私有快照能唯一确认真实持仓和成交，按正式 `OPEN` 记录。
- 如果私有快照没有对应持仓，或缺少方向、入场价、数量等成交事实，不得伪造正式交易流水；改为在 `<项目根目录>/.crypto/position-watch/` 建立待补成交细节的持仓跟踪清单，并要求用户补最少字段。
- 如果用户说明仓位来自跟单、子账户、其他交易所或机器人，不能用当前 Binance 主账户 API 快照的“无持仓”判定已平仓；在用户明确说平仓前，跟踪清单保持 active，并标注 `active_until_user_says_closed=true`。
- 如果用户在对话中说“新开了”“已经开了”“按上一份报告开了”某个标的，即使没有方向、入场价和数量，也必须先把它写入 active 跟踪；已在 active 清单里的标的后续报告必须进入 `position_followups`，不能只作为新候选或摘要矩阵展示。
- 对跟踪清单里的每个标的，后续每次触发本 Skill 都必须先复核：相关新闻、官方公告变更、未来催化是否落地/延期/取消、是否进入兑现阶段、是否出现反向消息、价格是否触发关键失效位。
- 对 `pre_landing` 仓位，重点跟进事件前 24 小时、事件当天和事件后 24 小时：落地前看抢跑与失效，落地后看兑现/反转，不要把已落地事件继续当作埋伏理由。
- 使用 `crypto-news-analysis-report` 生成任何新 HTML 报告时，若 `<项目根目录>/.crypto/position-watch/` 中存在 active 跟踪清单，报告必须增加“已开仓催化落地跟踪”区块，逐项展示上次开仓时的催化、当前是否落地、是否延期/取消、最新相关新闻、关键失效位和下一次复核时间。不能只输出新的候选列表而漏掉已开仓标的。
- 对 active 标的，报告必须额外写清新闻对当前仓位是增强原逻辑、削弱原逻辑、需要降风险，还是只作为背景；缺少成交细节时仍要跟踪消息落地，只是不能计算盈亏、R 倍数或仓位风险。
- 每个 `coin_reports` 和 `position_followups` 条目必须包含 `asset_profile`，依次说明资产类型、一级行业/赛道、细分模块、核心业务/协议用途、主要价格驱动、同风险簇和 2–4 句背景介绍。股票映射合约不能只写“半导体”，需区分 AI GPU、定制 ASIC/网络互连、DRAM/NAND/晶圆代工等业务；加密原生代币也要说明协议用途、价值捕获和所属赛道。
- 最终输出要明确列出 `持仓跟踪状态`：已正式记录 / 待补成交细节 / 只读快照未确认，并列出下一次复核时间点。

## 不可跳过的安全边界

- 默认只读。没有用户单独配置 Binance U 本位合约交易权限时，不调用写接口。
- 用户要求“只分析、不看仓位、不要开仓、输出 HTML 报告”时，必须切到 `crypto-news-analysis-report` 流程：只用公开消息和公共行情，不执行账户审计，不读取 `.crypto/config.json`；生成 HTML 后必须把 `[打开 HTML 报告](file:///absolute/path/report.html)` 和 HTML 绝对路径返回给用户，不能只说“已生成”。
- 用户没有明确要求下单、数量、杠杆或账户风控，仅说“选币/看机会”时，也要默认生成 HTML 报告；若同时做了账户审计，报告中只能展示必要审计摘要，不能写入密钥、账户标识或私有成交明细。
- 不需要也不得请求提现、转账、现货交易权限。
- 每次触发都先走 `crypto-risk-ledger` 的生命周期审计：读取本地上下文、比对 Binance 当前持仓/近期成交/保护单与项目根目录 `.crypto` 流水。没有私有快照时，不能给精确数量、杠杆或“可立即执行”的建议。
- “开吧”“按这个来”“就这个”不是交易确认。只有未过期草案对应的精确短语 `确认执行 TOKEN` 才能进入执行。
- 不承诺收益。月收益目标只能作为研究和复盘基准，不能成为放宽消息质量、盈亏比、止损或组合闸门的理由。
- 任何数据过期、来源不可追溯、净盈亏比不合格或保护单失败风险不可控时，结论应是观望或仅观察。
- 报告中的 `落地` 必须指利好/利空效应是否已经通过供需、基本面、价格结构、成交量/OI/资金费率或交易限制兑现，而不是事件本身是否已经发生。事件排期或完成状态单独写在 `事件/生效时间`、`未来催化节点`、`当前阶段`；不能把“事件未发生”等同于“利空未落地”，也不能把“事件已发生”等同于“利好已落地”。
- `初步落地` / `基本落地` 不是淘汰状态。只要仍有未完成传导、下一验证节点或可量化二阶段路径，就必须转入 `已启动确认池`，继续完成消息、四周期结构、衍生品和剩余净盈亏比分析；不得仅因“已经落地”停止研究。
- 二阶段分析必须写明 `已完成传导`、`未完成传导`、`下一验证节点`、`二阶段触发`、`保守目标`、`结构失效位`、扣费后的 `剩余净盈亏比` 和 `行情耗尽信号`。只有效应已充分兑现且没有后续路径，或剩余净盈亏比 `<= 1`，才可淘汰。
- 逐币新闻解释必须写透：先介绍标的背景和所属模块，再展开新闻事实、原始来源可靠性、关键数字、利多/利空因果链、反向解释、落地/定价证据和后续验证点；不能只写标题、来源和一句方向判断。股票代币还必须拆分底层公司消息、Binance 合约工具消息和正股交易时段确认。
- 生成 payload 时必须设置 `meta.report_contract="v5"` 并提供 `market_hotspots`；每个 `coin_reports` 和 `position_followups` 条目都要通过 `news_evidence` 或 `source_refs` 绑定对应消息，章节内直接显示可点击来源、来源层级、可靠性、关键数字和证据边界，不能只把所有链接堆在报告末尾。
- `风险与落地速览` 必须紧跟结论摘要，已开仓标的优先于新候选，并直接展示当前落地、关键失效/追入风险和现在动作；高风险、已抢跑、需降风险或禁止追入项必须醒目标红。
- 风险标签必须贴合用户执行语义：用户可能把 `低` / `中低` / `中` 当作可开仓信号，因此只要消息未落地、仅为财报前预期/分析师观点/主题扩散、触发未收盘确认、回踩未承接、股票代币正股时段未验证、或只是“可继续跟踪/等待突破”，就不得把 `追进去风险` 标为 `中` 或更低；必须标 `中高` / `高` / `极高`，并明确写 `等触发` 或 `只观察`。每个 `中` 或更低风险标签都要解释“为什么现在可以开而不是只观察”；解释不出来就上调风险。
- 下架、停止开仓、自动结算类题材必须额外评估中途最大不利浮动（MAE）、短挤、盘口深度和资金费率/OI 拥挤。最终盈利不能证明入场质量好；如果没有 15m/1h 破位确认或冲高失败确认，追进去风险至少标 `高`，并显著降低仓位或只观察。
- 网络升级、硬分叉、治理执行、产品发布等事件抢跑仓出现浮盈后，必须提前定义 TP1、移动止损或关键位跌破退出。若缺少浮盈保护动作，不能只因为事件还未落地就建议继续硬扛；临近事件前 12-24 小时要主动复核是否降风险。
- 传闻必须隔离管理：未确认社媒/匿名内容只能进入 `传闻观察池`；至少两个独立可靠来源支持时可标 `corroborated`，但仍不可进入仓位测算；只有监管、交易所、项目方、公司等直接来源确认后才可标 `confirmed` 并进入核心候选评估。

## 标准工作流

1. **意图和时间锚点**
   - 记录当前绝对时间、时区、消息检索截止时间、用户目标周期和是否涉及真实下单。
   - 判断模式：`single` 单币精选、`basket` 多币滚动篮子、`medium_long` 数天至数周波段；多币埋伏默认启用 `basket`，一到三周持有默认启用 `medium_long`。
   - 用户要求“埋伏”“未落地之前”“提前布局”“未来催化”时，额外启用 `pre_landing` 模式：只把未来 1–30 天有明确节点、尚未完全兑现且有复核时间的事件作为提前埋伏核心；初步/基本落地但仍有下一阶段的标的转入 `已启动确认池`，只有效应已充分兑现且没有下一阶段的消息才只作背景。

2. **账户与生命周期审计**
   - 先让 `crypto-risk-ledger` 输出 `ledgerAudit`：本地 Wiki 是否读取、Binance 私有只读快照是否可用、真实持仓与本地流水是否对齐、差异如何处理。
   - 如果审计失败，只能继续公开信息研究或观察名单，不能输出精确交易数量、杠杆、保证金占用或确认草案。

3. **刷新并审计全市场底池**
   - 用户要求“选币”“扫币”或“全市场机会”时，先调用 `crypto-news-selector/scripts/build_universe_catalog.py`，不得从已有持仓或涨跌榜 Top-N 直接开始。
   - 读取生成的 `references/binance-usdm-universe.json`，披露 `total`、`contract_type_counts` 和 `market_type_counts`；确认全部普通永续和 TradFi 永续均进入后续过滤。季度合约只做覆盖审计，不与同底层永续重复推荐。
   - 按 `market_type` 区分加密币、美股/ETF/ADR、韩股、港股、A 股、商品和 Pre-IPO，并使用每条 `news_sources` 指向的官网、监管、交易所和媒体渠道取证。刷新失败时必须披露快照时间，不得称为实时全量扫描。
   - 强制披露分层计数：目录覆盖、24h 行情初筛、通过流动性门槛、实际消息核验、逐币分析完成、中高及以下风险写入报告、逐币深度章节、摘要淘汰。全市场流动性门槛固定为 24h 成交额 `>= 10,000,000 USDT`，不得提高门槛缩小工作量。清单里的 `news_sources` 只是渠道路由，不代表网站已逐条访问。
   - 机械过滤只能使用已披露的客观硬条件。过滤后的每个幸存标的都必须交给 `crypto-news-intel` 做本轮真实消息发现，历史对话、旧报告、已有排期和少量抽样搜索只能扩展查询，不能替代逐项访问。
   - 保存完整 `liquidity_survivors` 明细，并为每个幸存标的保存 `research_audit`：实际检查渠道/URL、查询词、检索时间、最新有效事件或 `no_valid_catalyst_found`、状态、原因、`analysis_completed=true`、`analyzed_timeframes=["1d","4h","1h","15m"]`、`market_data_time`、标准化 `chase_risk`、分析摘要、消息结论和结构结论。两个集合不一致，或 `researched_survivors` / `analyzed_survivors` 不等于 `post_filter_survivors` 时必须停止。

4. **信息差候选池**
   - 默认先让 `crypto-news-intel` 建立信息差池，而不是先用涨幅榜/跌幅榜/成交额榜决定候选。信息差池必须优先来自未落地公告、未来排期、链上/代币经济事件、交易所公告、财报/监管/产品节点、公司 IR/财报或可验证行业消息。
   - 每次先读取 `.crypto/rumor-watch/watchlist.json`，让 `crypto-news-intel` 对上次核验时间之后的公开传闻做增量扫描，并处理新增、交叉验证、官方确认、否认和过期状态。没有实际调度时只能声明已建立监控清单，不能声称后台实时监控。
   - 每份报告必须拆成三类候选：`提前埋伏池`、`已启动确认池` 和 `传闻观察池`。`提前埋伏池` 放未来 1–30 天有明确节点、尚未完全兑现、价格未明显抢跑的候选；`已启动确认池` 放涨跌幅/成交额已经启动，或效应已初步/基本落地但仍有二阶段路径的候选，继续评估剩余利润空间并等待回踩承接、突破后回踩或趋势延续确认；`传闻观察池` 放尚未得到直接来源确认的线索，只做核验与触发准备。
   - Binance `scan`、涨跌幅榜、跌幅榜、成交额榜、FinViz 或技术形态只能作为验证/补漏雷达，不能作为主入口；从榜单发现的币若找不到可追溯消息和未完全定价路径，最多标 `只观察` 或 `技术侦察`，不得进入核心消息面推荐。
   - 不倒推理由：不能先看到某币暴涨/暴跌，再强行匹配泛泛叙事、旧闻或无明确时间的消息。
   - 每轮读取最近报告历史，建立 `symbol/catalyst_id/reported_at/status/active_position` 索引。新候选默认冷却最近 3 份报告或 72 小时；同一催化 7 天内重复出现时只保留二阶段跟踪，除非有新的官方事实、事件状态变化、结构触发或定价证据。
   - 对重复标的计算 `repeat_count` 与 `repeat_penalty`：最近 5 份报告每出现一次加 1，同一催化重复额外加 2，上一轮已启动/已抢跑且无新证据额外加 1。`repeat_penalty >= 2` 不得进提前埋伏池，`>= 3` 不得进新候选矩阵。
   - active 仓位只进入 `position_followups`，不得重新包装为新候选。冷却/重复惩罚只影响候选层，不得从 `research_audit` 删除本轮已核验标的；每轮优先展示通过门禁且历史未出现的新标的，没有合格新标的时明确说明，不得用旧标的凑数。
   - 用户声明开仓时若未提供精确成交价，使用登记时的 `observed_price_at_tracking` 作为 `entry`，标记 `entry_source=user_declared_open_tracking_price`；该值用于研究和复盘基线，不声称是交易所成交回报。

5. **市场热点参考层**
   - 让 `crypto-news-intel` 基于完整行情底池和公开消息汇总市场状态、涨跌广度、成交额集中度、衍生品环境与主题扩散。
   - 每个主题标注 `萌芽/扩散/拥挤/退潮`、`低/中/高` 热度、代表标的、量价证据、共同催化、拥挤风险、公开来源和对选币的影响。
   - 热点只用于补漏、共振、降权和风险聚类。仅因属于热门主题，不得升级为候选、降低追入风险或绕过逐币消息与结构门禁。
   - 结构化结果写入顶层 `market_hotspots`；没有一致性热点时保留空 `themes` 并解释 `no_dominant_theme_reason`。

6. **消息面取证**
   - 让 `crypto-news-intel` 对机械过滤后的全部幸存标的逐项输出审计记录和分析结论，再输出 `newsBrief`：事件或无有效催化结论、来源、发布时间、事件发生/生效时间、检索时间、距当前多久、时效性等级、有效窗口、链接、影响机制、独立证据数、可持续性、已定价风险。
   - 批量或并行检索可以提高速度，但结果必须按标的落账；不能以行业新闻覆盖同赛道全部币，也不能因为某标的未出现在历史排期中就跳过。
   - 单币核心机会要求高质量来源；社交传闻只能作线索。缺少明确时间或时效性等级的消息，不得进入核心候选。
   - 对传闻额外输出 `rumorBrief`：`first_seen_at`、`last_checked_at`、来源层级、支持/否认证据、`lead/corroborated/confirmed/disputed/rejected/expired` 状态、下一次复核时间、价格触发和失效条件。`lead` / `corroborated` / `disputed` 固定为 `只观察`，禁止传给 `crypto-risk-ledger` 做仓位测算。
   - `pre_landing` 模式中，`newsBrief` 还必须包含 `未来催化节点`、`当前阶段`、`剩余时间`、`利好/利空落地程度`、`是否已被抢跑`、`兑现风险`；初步/基本落地但尚未完全兑现的标的转入 `已启动确认池` 继续分析，只有没有未来节点且利好/利空效应已充分兑现的消息才不得进入核心候选。
   - 参考 B 站等二级内容学习到的消息面方法时，只能沉淀方法论：先找信息差、再做量价确认、叙事/新项目优先但必须过流动性过滤、空投/活动先做安全识别。B 站、KOL 或视频标题/简介不能单独作为交易核心事实来源。

7. **行情结构确认**
   - 让 `crypto-market-structure` 为全部通过 1000 万 USDT 门槛的标的输出 `marketBrief`：1d/4h/1h/15m 方向、触发位、结构止损、保守目标、ATR/成交量/流动性、是否允许市价或近价限价。
   - 消息成立但价格已经冲高回落、量价背离或关键结构失效时，不追单。

8. **综合评分与计划生成**
   - 将 `newsBrief` 和 `marketBrief` 合成候选矩阵，标注 `可开仓`、`差一项触发`、`只观察`、`淘汰`。
   - 所有标的完成逐项分析后统一评定追进去风险；`低/中低/中/中高` 的全部标的必须进入候选矩阵和逐币深度报告，不设展示数量或篇幅上限。`高/极高` 可只保留在逐项研究审计中，但不得省略分析摘要；只有交易计划数量继续受账户和组合风险限制。
   - 只有可追溯消息、行情结构、流动性、净盈亏比和组合风险都通过，才让 `crypto-risk-ledger` 计算数量、杠杆和组合风险贡献。
   - 如果候选仍是“差一项触发”或“只观察”，风险文案必须避免让用户误读为可开仓；尤其是股票代币财报前预期票，不允许因为 RSI 不极端就写 `风险中`，应写 `中高/高，等触发`。
   - `pre_landing` 模式不是“事件还没发生所以风险低”。只有未明显抢跑、价格仍靠近可控低吸区、结构止损近、且未来节点可核验时，才允许给 `中` 或更低追进去风险；否则必须 `中高/高`。

9. **执行草案或手动计划**
   - 用户要求自动执行时，只让 `crypto-trade-executor` 为一笔“当前仍满足门禁的市价计划”生成短时草案。
   - 先完整展示方向、数量、杠杆、保证金模式、止损、分级止盈、有效期和确认短语；等待用户精确回复。
   - 用户未精确确认前，最终回答只停在研究计划或订单草案。
